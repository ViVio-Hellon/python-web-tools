# ランチャー連携(業務ツール統合ランチャー)

「ランチャー連携 要件定義」の **3. 各ツール側への依頼** と **10. 起動完了の確認** に、
総合ツールとして答えるページです。

- 相手: 業務ツール統合ランチャー(`python-business-tools-launcher`。1.6.4 の作りで確かめた)
- 約束: ランチャーは**ツールごとの分岐を持たない**。起動ファイル・`config/app.json`・
  起動ファイルの隣の `stop.bat`・`/api/health` だけを見て扱いを決める。
  ツールの中の流れ(exe → Python → 画面)は、このツールが引き受ける。

---

## 1. 起動方法(3.1・3.3・3.4)

ランチャーに登録してよい起動ファイルは次の3つです。**どれもランチャーからそのまま実行できます。**

| 起動ファイル | 何が起きるか(中の流れはツール側の責任) | 画面 | ランチャーの［画面］ |
|---|---|---|---|
| **`梱包資材総合ツール.exe`**(デスクトップ版) | exe(Tauri)→ Python(`bridge.py`)を子として起こし、標準入出力でやりとり。**ポートを使わない** | アプリ自身の窓 | アプリの窓 |
| **`Start.vbs`**(ブラウザ版・ふだん用) | `pythonw start_app.py`(コンソールなし)→ 127.0.0.1 で待ち受け → 画面 | ランチャーの専用画面(`--no-browser` が届くとき) | ブラウザー |
| `start.bat`(ブラウザ版・診断用) | `python start_app.py`。経過と失敗の理由をコンソールに出す。ランチャーから呼ぶとコンソールは出ず、最後の `pause` も素通り | 同上 | ブラウザー |

- **1台の PC にはどれか1つを登録**してください。exe と Start.vbs は同じ `config/app.json` を読むので、
  アプリIDが同じ(`nlm.packaging-tool`)になり、ランチャーは2つ目を保存できません。
  移行の途中で両方を並べるときは、exe の行のアプリIDを `nlm.packaging-tool.desktop` などに変えてください。
- **`Start.vbs` は受け取った引数を `start_app.py` へそのまま渡します**(VER4.7.0 から)。
  ランチャーはこれを見て［起動引数］に `--no-browser` を自動で入れ、起動を確かめてから
  自分の専用画面を開きます。止めるときにその画面も閉じられます。
  ダブルクリックで起動したときは引数が無いので、今までどおりツールがブラウザを開きます。
- 現場・資材のどちらで開くかは、**この端末に許されたモード**(アクセス権限マスタ)で決まります。
  ランチャーの設定でモードを分ける必要はありません。ただしポートは違います(→ 4)。

## 2. 起動して落ちないことの確認(3.2)

| 確かめたこと | どこで | 結果 |
|---|---|---|
| exe を起動し、窓の画面が Python から届く・どのプロセスもポートで待ち受けない | GitHub Actions(Windows)・この開発環境(Linux) | OK |
| exe を**もう一度**起動すると、窓を出さずにすぐ終わる(戻り値 0)。1つ目は動いたまま | 同上 | OK(Linux)/ Windows は Actions で毎回確かめる |
| exe の窓に「閉じて」(WM_CLOSE)と頼むと、×と同じ確かめを通って**自分で**終わる(戻り値 0、Python も残らない) | GitHub Actions(Windows) | 毎回確かめる(`scripts/desktop_smoke.py`) |
| `start_app.py --no-browser`(Start.vbs が引数を渡したとき)で起動し、ランチャーのコードで登録・起動確認・停止 | この開発環境(ランチャーの `tool_registry` / `health` / `process_manager` をそのまま使用) | OK(下の 3・4) |

確かめていないこと: Windows の実機で、ランチャーの画面から押す一連の操作(wscript 経由の Start.vbs、
専用画面の開閉)。exe の WM_CLOSE は Actions の Windows で確かめます。

## 3. 終了方法(3.5)

| 止め方 | 動き |
|---|---|
| 画面の［終了］ | 保存していない図・実行中の処理があれば訊く。「終了する」なら止める |
| デスクトップ版の窓の × | ［終了］と同じ確かめ |
| ブラウザ版のタブを閉じる | 8 秒で自動終了(画面が1枚も無くなったとき)。無通信 90 秒でも終わる。**保存していない図は閉じる前に訊く** |
| `stop.bat` | このツールだけを止める(下の表)。`--force` で実行中の処理を中断してでも止める。`--status` は見るだけ |
| `POST /api/shutdown` | ブラウザ版の停止要求。トークン(`X-Tool-Token`)が要る。ロックファイルに入っている |
| ランチャーの［ツール停止］ | 次の 4 |

**どの止め方も、保存していない図・実行中の処理があれば止めずに理由を返します**(HTTP 409)。
理由は `running`(一覧)と `message`(文)の両方に入れています。ランチャーと `stop.bat` は `running` を読みます。

```json
{"stopped": false, "reason": "unsaved",
 "running": ["保存していない変更(簡易在庫の保管位置マップ)"],
 "message": "保存していない変更があります(簡易在庫の保管位置マップ)。保存せずに終了しますか?"}
```

`stop.bat` の戻り値:

| 戻り値 | 意味 |
|---|---|
| 0 | 止めた/もともと動いていない |
| 1 | 止めなかった・止められなかった(保存していない図・実行中の処理を含む。理由は画面に出る) |

**プロセス名で一括に止めることはしません。** `stop.bat` はまず `/api/shutdown` で頼み、応答が無いときだけ
ロックファイルに記録した PID を使います。その前に、その PID のコマンドラインにこのツールの置き場所が
入っていることを確かめます(`process_manager.py`)。

## 4. ランチャーから止める(3.6)

ランチャーの［停止方法］は **auto のまま**で止まります。総合ツール専用の止め方はありません。

| 起動ファイル | ランチャーがすること | 保存していない図・実行中の処理があるとき |
|---|---|---|
| exe | 窓に「閉じて」(WM_CLOSE)と頼む = × と同じ | ツールの窓に確かめが出る(ランチャーが窓を前に出す)。ランチャーの［ツール停止］には「強制終了する」が出る |
| Start.vbs / start.bat | 隣の `stop.bat` → `POST /api/shutdown` → PID(照合してから) | 止めずに「保存していない変更(…)」と出し、「強制終了する」が出る。押すと `stop.bat --force` → `{"force": true}` で止まる |

ランチャーのコードで確かめた結果(この開発環境、ブラウザ版):

```
[OK] 登録で読む値: app_id=nlm.packaging-tool / 表示名=梱包資材総合ツール / ポート 8713
[OK] Start.vbs の起動引数の自動判定: '--no-browser'(VER4.6.5 までは '' で、ツールがふだんのブラウザーに開いていた)
[OK] 起動完了(ready)を確かめた(0.8秒)
[OK] 停止用のトークンをツールのロックファイルから拾えた
[OK] 保存していない図があると止めない: busy=['保存していない変更(簡易在庫の保管位置マップ)']
     (VER4.6.5 までは「実行中の処理があります: (不明)」と出ていた)
[OK] 「強制終了する」で止まった → ツールが自分で終わった(戻り値 0)・ロックファイルが片付いた
[OK] ふだんの［ツール停止］で止まった(戻り値 0)
```

## 5. 起動完了の確認(10)

### ブラウザ版: `GET http://127.0.0.1:<ポート>/api/health`

```json
{"app_id": "nlm.packaging-tool", "ready": true, "stage": "起動完了", "stage_key": "done",
 "pid": 1234, "port": 8713, "mode": "field", "version": "4.7.0", "app_root": "C:\\業務ツール\\総合ツール"}
```

- **`app_id` が `nlm.packaging-tool` で、`ready` が `true` なら起動完了**。`ready` が `false` の間は
  `stage` に今の段(「準備しています」など)が入る。ランチャーの進み具合の窓にそのまま出せる。
- トークンは要らない(業務データを返さない)。
- ポートは**端末のモードで違う**: 現場 **8713**、資材 **8723**。使われていれば 3 つ先まで繰り上がる
  (現場 8713〜8716、資材 8723〜8726)。ランチャーは設定と違うポートで動いていても見つけるが、
  資材の端末ではランチャーの［ポート］を **8723** にしておくと最初から合う。
- いま実際に使っているポートと PID は `%LOCALAPPDATA%\PackagingTool\runtime\field.lock`
  (資材は `material.lock`)にも書いてある。

### デスクトップ版: ポートが無い

- ランチャーは**窓が出たこと**で起動を確かめる(ランチャーの［画面］= アプリの窓)。
  窓はすぐに出て、中に「起動しています」→ 準備ができたら画面、の順に出る。
- **ランチャーの［ポート］は空にしてください。** ［＋ ツールを追加］で exe を選ぶと
  `config/app.json` の 8713 が入りますが、デスクトップ版はそこで待ち受けません。そのままだと、
  ランチャーは起動確認が答えないと見て、**起動から 90 秒の間は［ツール停止］が「窓を閉じてもらう」
  手ではなく PID の手に回り**、90 秒たつと「起動を確かめられない」の障害記録を書きます。

## 6. ランチャーへの登録(配布先設定の例)

| 項目 | デスクトップ版 | ブラウザ版 |
|---|---|---|
| 起動ファイル | `C:\業務ツール\総合ツール\梱包資材総合ツール.exe` | `C:\業務ツール\総合ツール\Start.vbs`(または `start.bat`) |
| 起動引数 | 空 | `--no-browser`(［自動］で入る) |
| ポート | **空** | 現場 8713 / 資材 8723 |
| 停止方法 | auto | auto |
| 画面 | アプリの窓 | ブラウザー |

## 7. ランチャー側への申し送り(提案。ツールごとの分岐ではありません)

1. **Tauri と見分けた exe でも `app.json` のポートを拾う。** 中に Web サーバーを持たない Tauri の exe では
   起動確認の URL が答えず、それまでの間は停止が PID の手に回り、90 秒後に障害記録が書かれる。
   今は［ポート］を空にして避けている(→ 5)。
   ツールの `app.json` に起動ファイルごとの［画面］を書ける形があれば、手で直さずに済む。
2. **`stop.bat` の戻り値を見ていない。** 保存していない図があると `stop.bat` は戻り値 1 ですぐ終わるが、
   ランチャーは止まるのを最大 20 秒待ってから `/api/shutdown` に進み、そこで理由を出す。
   戻り値が 0 以外ならすぐ次の手へ進めば、20 秒待たずに理由が出る。
