# 変更履歴

版は `config/app.json` の `version` **ただ1つ**が出どころです。
画面の帯のバッジ・起動待機画面・設定画面・`GET /api/health` は
すべてここを読むので、**上げる場所は1か所**です。

```json
{ "version": "1.0.0" }
```

---

## 版の上げ方

`メジャー.マイナー.パッチ` の3つの数字だけを使います。
判断の基準は「**現場が何をし直すことになるか**」です。

| 桁 | 上げるとき | 現場に起きること |
|---|---|---|
| **メジャー** | 手順が変わる。押す場所・並び・言葉が変わる | 覚え直しが要る。事前に周知する |
| **マイナー** | できることが増える。既存の手順はそのまま | 触らなければ今までどおり |
| **パッチ** | 直しただけ。見た目も手順も変わらない | 何も要らない。黙って入れ替えてよい |

判断に迷ったら**大きいほうへ寄せます。** 「変わらないと思っていたら
変わっていた」は、現場が画面を信用しなくなる出来事だからです。

### 上げるときの手順

1. `config/app.json` の `version` を書き換える
2. このファイルの先頭に、その版で何が変わったかを1節足す
3. 試験を通す(`python3 -m unittest discover -s tests -t . -q`)
   ── 版の書き方は `tests/test_app_config.py` が機械で見ています

配るときは**フォルダごとコピー**します。入れ替えたあとに現場から
「どれが入っているか」と聞かれたら、画面左上のバッジを読んでもらえば
答えられます(`VER2.18.0`)。

> **上げ忘れは機械が見ています。** `tests/test_app_config.py` が
> 「`config/app.json` の版に対応する節がこのファイルにあるか」を確かめる
> ので、版を上げずに配ろうとすると試験が落ちます。逆に、版を上げたら
> ここに1節足すまで試験は通りません。

## VER2.40.0

### 配置図のボード色にもっとメリハリを付けた(VBAの色相のまま濃さを強調)

現場の声:「ボード配置描写の色周りをもっとメリハリをつけてほしい。
デフォルトでキャンバスに色を付けているからボードの配色も濁って見える
のでは。ここに関してはVBAに寄せても良い」。

**原因**: VER2.37.0で図の地(キャンバス)を資材ごとに淡く色分け

地とボードがほぼ同じ明るさで重なり合い、境目が見えにくくなっていた
(下用は明暗どちらのテーマでもコントラスト比 1.0〜1.4:1 しかなく、
特に暗いテーマでは地とほぼ同色で塗りが消えていた)。

**修正**: 色相はVBAのまま(上用=赤系/下用=緑系/補填=黄系)、濃さだけを
地からはっきり離した。輪郭色(`--mat-upper-line`等)も塗りとの区別が
付くよう合わせて調整した。`scripts/check_contrast.py` で明暗3テーマ
すべて確認済み(WCAG 部品3:1以上を維持)。

## VER2.39.1

### 下用の丈補填を上用と同じ規則(丈残400超→主サイズ継続/以下→100mm)に統一

現場の声:「ボード選定時、主サイズ決定⇒残り丈400越えの場合、主と同じ
サイズのボードを使用/残り丈400以下⇒100補填で丈を埋める(4回まで)に

**修正**: 下用・上用共通の `_run_main_or_fixed_length_fill()` に一本化し、
どちらも「丈残400mm超→主ボードを1枚増やす(同サイズ継続)/400mm以下→
100mm固定サイズをCeiling(丈残/100)枚(最大4枚)追加」という同じ規則に
揃えた。定数も `LENGTH_FILL_THRESHOLD`/`LENGTH_FILL_BOARD_W` として
上下共通化した。

## VER2.35.2

### ボード選定ロジックの再監査で見つかった3件を修正

選定ロジックだけに絞ったゼロベースの再監査で見つかった、実際に
コードを追跡して確認した問題を修正した。

- **`select_lower_boards` の業界標準サイズ("1×2"/"4×8")ショートカット
  に `is_protec_mode` のガードが抜けていた。** docstringには「通常
  モードのみ」と明記されていたが実装は素通しで、上用側の同名
  ショートカット(こちらは正しくガードしている)と非対称だった。
  プロテック選定が適合する在庫を見つけられず通常フローへフォール
  バックした場合に発動しうる経路で、下用だけプロテックの業務ルール
  (`ProtecCutResult`)を一切通さず標準サイズを即採用し、上用は
  (protec_resultが無効なので)独自に通常選定へ進んでしまうため、
  「プロテックなのに上下が別ボードになる」不具合につながる。
  ガードを追加して上用側と揃えた。

- **`sort_boards_by_target_width`(下用の非strict判定)が、対象幅に
  「近い方」ではなく「大きい方」の向きを採用していた。** 上用
  (strict、fit_limit=target_width)ではこの2つは数学的に一致するが、
  下用(fit_limit=target_width×1.2、20%はみ出し許容)では一致しない。
  20%はみ出す向きが「大きい」という理由だけで採用され、しかも
  はみ出し側は直後の不足ペナルティ(gap_ratio)が掛からないため
  無罰則の好条件として扱われていた。実際の選定
  (`get_best_orientation`経由)は常に対象幅に最も近い向きを採用する
  ため、候補の並び順(ランキング)と実際の評価基準が食い違い、
  本来先に評価されるべき候補が並び順で後回しにされることがあった
  (既知の「1000×2000 vs 1030×1520」問題と同じ根の、より一般的な
  ケース)。対象幅に最も近い向きを採用するよう揃えた。

- **`decide_protec_orientation` が、カット不要な向きより絶対距離が
  近いカット要の向きを選んでしまうことがあった。** 「製品幅より
  わずかに超過(カット要)」が「余裕を持って不足(カット不要)」より
  僅差で近いというだけでカット要の向きを選ぶのは、在庫の種類が
  少なくカットを避けたいというプロテックの業務上の前提と整合しない。
  カット不要な向きがあれば常にそちらを優先し(その中で最も近いもの
  を選ぶ)、無い場合だけ従来どおりカットが要る向きの中から最も
  近いものを選ぶように変更した。

いずれも既存のテストで検出されていなかった(既存のボードサイズの
組み合わせでは症状が出にくい条件だった)ため、それぞれ症状を
再現するテストを追加した。

## VER2.35.1

### 上用の丈補填ロジックを、VBA側の仕様更新に合わせて作り直した

VBA側で仕様が更新されたのに合わせて移植した。

- **`SelectUpperBoards`(上用丈補填フェーズ)**: 丈残が400mm以下の
  ときの小型補填を、旧来の「在庫全体から短辺の近さで最大5回探す」
  ループから、「100mm板をCeiling(丈残/100)枚、最大4枚」という単純
  計算に置き換えた。丈補填は「マイナス(未カバー)は禁止・超過は許容」
  というルールで、丈残400mm以下という前提があれば100mm板の追加だけで
  必ずカバーできるため、通常サイズまで候補に含めてしまい後から幅不足に
  気づいて後追い幅補填する二階建て構造になっていた旧ロジックは不要に
  なった。専用定数 `UPPER_LENGTH_FILL_BOARD_W`(=100)を新設し、
  幅不足補填の `smallSizes`(30/50/100)とは切り離している。
  「丈不足強制追加」ブロック(安全弁)と「幅不足補填」ループは
  変更していない。

- **`PlaceLengthFillBoards`(丈補填ボードの配置)**: 幅方向を無条件で
  `limit_w`(製品幅/パレット幅)まで引き伸ばしていたため、在庫の実サイズ
  (長辺)より大きい架空の寸法で配置されていた(例: 在庫295×1080なのに
  1122×295として配置=面積が水増しされる)。在庫の実際の長辺と
  `limit_w` の小さい方を使うようにし、在庫の長辺が `limit_w` を超える
  場合だけ実際にカットが発生する扱いにして、その旨を配置側の
  `cut_info` に記録するようにした。

## VER2.35.0

### 業界標準サイズ("1×2"/"4×8")が、先に見つかった別サイズに負けて選ばれないことがあった

現場の声:「製品1002×2002で、業界標準サイズ"1×2"(1000×2000、カット
不要)ではなく1030×1520(差0mmだが継ぎ足しカットが必要)が選ばれて
いた」。

原因は下用・上用とも、ボード選定(PASS1)が「候補を幅の一致度順に
並べ、最初に見つけた1件で即決定する」設計になっていること。
1030×1520が候補リストの先頭に来ると、そこで選定が打ち切られ、
後方にあった1000×2000は一度も評価されなかった。

PASS1本体(全ケースに影響する一般ロジック)を作り直すのはリスクが
大きいため、"1×2"(幅997〜1005/丈1997〜2005 → 1000×2000)・
"4×8"(幅1248〜1255/丈2499〜2505 → 1250×2500)という業界標準の

### プロテックの丈カット判定に、記録漏れと二重記録の両方があった

## VER2.34.1

### プロテックの丈方向も、100mmを超えたらカットするようにした

VER2.34.0 で「プロテックは丈方向を枚数で吸収し、丈カットは基本的に
発生しない」という前提で作ったが、これは正しくなかった。MAP画面の
カット線描画(`recalc_length_cut_info`)と切断依頼書
(`protec_cut_size_info`)が別々の判定基準を持ってしまうと、画面には
カット線が出るのに依頼書には丈カットの行が出ない、という食い違いが
起きうる。

正しい判定基準は「超過量」ではなく「フルサイズで覆いきれない残りの
長さ」(lenRemainPL):

    lenRemainPL = 対象丈 - (1枚の丈 × フルサイズで収まる枚数)
    lenRemainPL が 100mm を超える → カットして1枚追加する
    lenRemainPL が 100mm 以下     → 切り捨てて無視する

(例: 1枚1000mm・対象丈2910mmなら、フルサイズ2枚[2000mm]の残り
910mmが100mmを超えるので、3枚目を910mmにカットして追加する。
対象丈2050mmなら残り50mmは100mm以下なので、2枚のみで追加しない)

この判定を行う関数(`decide_length_count_with_cut`)を1か所に置き、
下用選定・上用選定(それぞれ対象丈が異なる。下用はパレット丈、
上用は製品丈)・MAP画面のカット線・切断依頼書のすべてがこの結果を
参照するようにした。以前のように、それぞれの処理が「丈カットが
必要か」を別々に計算し直すことはない。

在庫の種類が少ないプロテックの特性上、通常は丈カットが発生しない
場面が多いが、発生する場合はMAP画面と依頼書の内容が必ず一致する。

## VER2.34.0

### プロテックモードのカット依頼周りを、選定→配置→帳票が同じ確定値を使うように作り直した

現場の声:「カット依頼出力が正しく出力されない」「プロテックモードで
上用ボードが製品幅を超過するケースでは、TryPlaceInsidePaletteが
静かに失敗し、placedBoardsに一切登録されない」。

以前は、下用選定・上用選定・配置・カット依頼書のそれぞれが、幅カット
の要否やカット後サイズを**別々に再計算**していた。計算の元になる
考え方(丸め方、境界条件)が微妙に食い違うことがあり、選定では
成立していたはずのボードが配置段階で弾かれて1枚も置かれない、
カット依頼書の数字が選定結果と合わない、といった不具合が起きていた。

今回、次の型を新設し、「選定が決めた1つの正解を、後続の全処理が
使い回す」設計に作り直した。

- `ProtecCutResult`: プロテック専用の選定確定値(向き・カット後サイズ・
  カット要否・枚数)を持つ器
- `decide_protec_orientation`: 1つの在庫サイズについて、どちらの
  向きを使うか・カットが必要か・カット後の幅はいくつかを判定する
  共通ロジック。下用の自動選定と、上用の下用コピー判定の**両方**が
  これを通る

これにより、下用選定(`select_protec_lower_boards`)→上用選定
(`select_upper_boards`)→配置(`place_boards_from_list`)→カット依頼書
(`protec_cut_size_info`)が、同じ`ProtecCutResult`をそのまま使い回す
ようになった。手動でボードを増減した後(自動選定の結果を捨てたあと)
でも、配置・カット依頼の直前に同じ判定ロジックで確定値を作り直す
(`apply_protec_rules_to_lower_list`)ので、経路によって結果が
食い違うことがなくなった。

**プロテックは上用・下用とも「製品幅より小さくてよい許容量」の
範囲でしか使えない**(1P1216は-10mm、それ以外は-80mm。以前の実装は
1P1216を誤って-5mmにしていたので、あわせて訂正した)。上用だけ
製品幅を超えて配置してよいという誤った理解で一度実装してしまった
箇所があったが、上下とも製品幅を超えてはいけないという正しいルールに
訂正している。

在庫の種類が少なく、複数種を組み合わせる余地がほとんど無いという
プロテックの特性を踏まえ、幅カットが必要と分かった時点で早期に
「カット前提」の扱いに倒すようにした(通常ボードのように、主選定→
補填→カバー不足の確認、という段階を踏まない)。

丈方向は同じボードの枚数を増やすだけでカバーする設計とし、丈カットは
基本的に発生しない。

## VER2.32.1

### 引当行の切り替えを「受注番号」ではなく「引当NO」で行うようにした

VER2.32.0 で足した引当行クリックの切り替えは、押された行を**受注
番号**で特定していた。データの流れを確認したところ、正しくは
SIKALOTNOW から LOTNO で1行 → SIKAHIKINOW で同じLOTNOの行の中
から**引当NO**で1行(ここで引当NOとオーダーNOが決まる)→
SIKAODRNOW で同じオーダーNOの行を展開、という順で辿るもので、
**主語は「引当行」であって「受注番号」ではない**。

1ロット内では受注番号は基本的に重複しないため、通常の使い方では
どちらの特定方法でも結果は変わらない。ただし、押した行を主語に
していないと、万一の状況(同じ受注番号を持つ引当行が複数ある場合)に
どちらの行を指しているか決まらなくなる。データの流れどおり、
引当NOで行を特定してから受注番号を取り出す形に直した
(`GET /api/lot/<ロット番号>/hiki/<引当NO>`)。

## VER2.24.0

### 「壊れているのか、読み方の問題なのか」を言い切る道具

文字化けの原因は2つに1つで、**直し方がまったく違う。**

    (A) 読み方の問題       … ファイルは無事。取り込み直せば直る
    (B) 元のファイルが壊れている … 変換の時点で字が失われている。
                              取り込み直しても直らない。変換をやり直す

**画面の文字を見比べても、この2つは区別が付かない**(どちらも同じように
化けて見える)。バイトを見れば区別が付くので、それをする道具を用意した。

    python3 scripts/check_encoding.py

取り込み元を直接調べ、判定した文字の入れ方・**すでに `\ufffd` が
焼き付いていないか**・判定した入れ方で読めない値が無いかを出し、
(A) と (B) のどちらなのかを結論として書く。

`\ufffd` は「読めなかった字」の跡で、そこに元のバイトはもう無い。
取り込み元にこれが入っていたら、こちらで何を直しても戻らない ──
**その場合に「取り込み直してください」と案内してはいけない。**

## VER2.23.0

### 文字化け ── 取り込む前に化けないようにする

VER2.22.0 の対応は「化けた行を見つけて取り込み直させる」という後始末
だった。**そもそも化けさせないのが先**という現場の指摘を受けて、
読み方そのものを作り直した。

**なぜ VER2.20.0 の直しでも化けたのか。** 値ごとに「まずUTF-8、駄目なら
CP932」と試していたが、これが間違いだった ── CP932のバイト列が、
たまたま**正しいUTF-8としても読めてしまう**ことがある。

    CP932 の `燿　` = e0 a0 81 40  →  UTF-8としても妥当で `ࠁ@` と読める

例外も出ず `�` にもならないので、**静かに化けて**そのまま手元へ入る。
機械で数えたところ、この形の組み合わせは実際に多数存在する。

**ファイル単位で決めれば取りこぼさない。** 変換ツールは1つのファイルを
1つの入れ方で書き、本物のUTF-8ファイルにはUTF-8として読めない値が
1つも無い。そこで開くときに中身を標本抽出し(`sniff_encoding`)、
日本語を含む値の多数決で入れ方を決めてから読む。1つの値では決めない
── UTF-8のファイルに壊れた値が1件混ざっているだけで全体をCP932と
読むと、その1件を助けるために残り全部を化けさせることになる。

### 表名・列名まで CP932 で読んでいた

上の対応中に見つけた。**SQLiteの識別子は必ずUTF-8**だが、
`sqlite_master.name` と `PRAGMA table_info` は識別子を**値として**返すので、
CP932で読む設定を掛けたままだと `ﾛｯﾄ番号` が `ﾛｯﾄ逡ｪ蜿ｷ` になる。
その名前では引けないので、**表が丸ごと空で取り込まれる**。
識別子を読むあいだだけUTF-8に戻すようにした(`identifiers_as_utf8`)。

### どちらでも読めないバイト列を黙って潰さない

元のファイルが壊れていて両方の読み方で失敗した場合だけ、これまでどおり
読めた字を残す。ただし黙って `�` にせず、記録に残して警告を出す。

### 文字化け(2回目)── 直していた分岐が、そもそも通らなかった

VER2.18.0 では `import_specs._text` の「値が bytes で返ってきたとき」に

読む側に手を入れるしかなかった。

取り込み元の接続に `text_factory`(`source_db.decode_text`)を挿し、

同じ原因で **「取り込み直してもマスタが表示されない」も起きていた** ──
列を1つ読めないだけで例外が飛び、その表の取り込みが丸ごと見送られて
いたため(`data_sync` が表単位で握りつぶす)。

取り込みは総入れ替えなので、開いたままの一覧はその時点で古い。
ジョブ完了時に一覧を読み直すようにした(編集の途中なら触らない ──
打ちかけの内容を本人の操作以外で消さないため)。

- `mode:materia` ── `mode:material` の打ち間違い(末尾の `l` が無い)

  意図的に効かせていない

指摘はしていたが、**指摘だけでは直せなかった。** 打ち間違いは
近い正しいコードを併記し(`mode:materia → mode:material のことですか?`)、
条件が空の行には**その端末のログインID / PC名そのもの**を出すようにした。

### パレット検索の行に「当たり方」を出す(2回目)

回転したのか・厳密に収まったのか・許容差(+5mm)でようやく入ったのかは

### 選定ログの詳細化(2回目)

- パレット確定・製品サイズ確定(**断ったときも**、その理由まで)

- ボード自動選定(前提・候補数・疲労度の有無・**選ばれた1枚ずつ**)

## VER2.9.2

**取り込みの進捗表示で、テーブル単位の失敗と画面のレーン(段ごとの
カード)が食い違っていた不具合を直しました。** 内部処理のみで、
押す場所も操作も変わりません。

### 何が起きていたか

設定画面の「取り込み」を実行すると、テーブルごとに進んでいく様子を
レーンのカードで見せている。1テーブルが読み込みに失敗しても
残りは続ける設計で、失敗は最終的なまとめ(`取り込みログ`)には
正しく出ていた。

ところが、**レーンの各カードの成否**は別の仕組みで決まっていた。
進捗は「いま何をしているか」という文言が変わった時点を段の区切りと
みなす。文言が変わらないと段は閉じないので、1つのテーブルが失敗
しても、そのことを段に書き込む手段がそもそも無かった。次のテーブル
の段が始まった瞬間に前の段は(成否を記さないまま既定値の"成功"で)
閉じてしまい、失敗を報告できるのは**たまたま最後だったテーブルの
段だけ**という状態になっていた。

その結果、「まとめ」には「◯◯: 取り込めませんでした」と出ているのに、
レーンのカードは(最後のテーブルでない限り)すべて緑の"完了"のまま
という食い違いが起きていた。写真で送っていただいた画面もこの状態で、
ログは失敗を指しているのにレーンは完了に見えていた。

### どう直したか

進捗の通知に「いまの段は問題なく進んでいるか」を追加した
(`progress(pct, message, ok=False)`)。文言は変えずに ok だけを
送れるようにし、テーブルの読み込み・列不足・書き込みのいずれかで
失敗したときは、その場でいまの段に失敗の印を付けるようにした。

あわせて、処理が正常に戻ってきた場合は最後の段の成否を全体の結果で
上書きしないようにした(以前は、途中のテーブルが原因で全体が失敗に
なると、無関係な最後のテーブルの段まで巻き添えで失敗と表示されて
いた)。処理そのものが例外で丸ごと落ちたときだけ、開いたままの段を
失敗と記す(その段は何も報告できずに終わっているため)。

### 現場に起きること

**操作は何も変わりません。** 取り込みが一部失敗したとき、レーンの
カードが実際に失敗したテーブルを正しく指すようになります ──
「まとめ」の文言とレーンの色が一致し、どのテーブルで何が起きたかが
画面だけで分かるようになります。

## VER2.8.0

**簡易在庫の「保管位置」でも配置編集ができるようになりました。**
あわせて、**背景の写真に合わせこむための拡大縮小**を両方の図に

### ① 簡易在庫の保管位置を、画面から直せます

これまで保管位置の図を直す手立ては画面にありませんでした
(`pallet_map.json` を手で書き換えるしかない)。棚検索の配置図には
配置編集があるのに、こちらだけ無かったのです。

図に無い位置の在庫は「図に無い位置に在庫があります」と出るので、
増えたことには気づけます ── 気づけるのに直せない、という
行き止まりでした。

棚検索と**同じ約束**にそろえてあります(覚え直しを増やさないため)。

| | |
|---|---|
| 編集モードの入り切りが要る | 図はよく押す(在庫を見る)ので、常時ドラッグできると見るつもりの操作でずれる |
| 保存するまでファイルに触らない | 間違えて動かしても、開き直せば元に戻る |
| 足す・消す・背景の差し替え | 棚検索と同じ操作 |

### ② 箱の大きさを変えられます(両方の図)

出荷時の大きさは**どれも同じ四角**です。実際の棚は間口も奥行も
まちまちなので、写真を下敷きにすると箱だけが浮きます。

**右下の角を掴んで**大きさを変えられるようにしました。掴んだ角だけが
動き、**左上は動きません** ── どちらが動くのか分からない操作は、
合わせこみの邪魔になります。

小さくしすぎて掴めなくなること、図より大きくして端が見えなくなること、
広げた結果はみ出すことは、いずれもサーバ側で止めます。

### ③ 背景の写真そのものをずらせます(両方の図)

写真の画角は図の枠と一致しないので、**枠いっぱいに引き伸ばすと必ず
ずれます**。これまでは引き伸ばすだけで、位置も倍率も動かせませんでした
(`floor_plan.json` にはもともと項目があったのに、使われていません
でした)。

「背景の合わせこみ」で **倍率・よこ・たて** を入れられます。
**箱は動きません** ── 箱を全部動かして写真に合わせるより、下敷きの
側を合わせるほうが早く、やり直しても箱の位置は壊れません。

掴んで動かす形にはしていません。箱を掴む操作とぶつかって、どちらが
動いたのか分からなくなるからです。数で入れると**同じ量を何度でも**
やり直せます。

### ④ 棚検索にも拡大縮小が付きました

## VER2.6.0

**アクセス権限マスタを、画面から作れるようにしました。**
これが無いあいだは**どの端末も現場モードだけ**になります。
「モードが切り替わらない」の原因が、ここでした。

### 何が起きていたか

アクセス権限はこのツールが後から足した表で、**既存の梱包資材マスタ
には入っていません**。無くても取り込みは失敗しません(無いことを
失敗と数えると、取り込みが毎回「失敗」と出て本当の問題が埋もれる)。

そのぶん、無いことがどこにも現れませんでした。

```
アクセス権限が無い
  → どの端末も現場モードだけ(締め出さないための既定)
  → 帯のモード切替に選択肢が1つしか出ない
  → 「切り替えが効かない」としか見えない
```

しかも直しようがありません。マスタ管理の一覧は**取り込み元にある表
だけ**を並べていたので、アクセス権限は画面のどこにも出ませんでした。
最初の1行を入れる場所が無い、という行き止まりです。

### どうしたか

**無い表も一覧に出します。**「まだありません」の札と、それが何を
意味するか(現場モードだけになること)を添えます。
「+ 取り込み元に作る」を押すと、取り込み元に空の表ができます。
あとは普段どおり「+ 行を足す」で登録します。

```
ログインID  PC名        権限            有効
(空)        NLM-PC-042  mode:material   1     … この端末は誰でも資材
yamada      (空)        mode:material   1     … 山田はどのPCでも資材
suzuki      NLM-PC-042  mode:material   1     … 鈴木がこの端末のときだけ
```

空欄は「問わない」です。**両方が空の行は効きません** ── それは
全員への許可で、権限を設ける意味が消えるからです。

### 作るのは、このツールが足した表だけ

PalletMaster のような上流の表は作りません。無いのは資材課側の事情
(ファイルが違う・移された)で、空の表を作ってしまうと**その事情が
「0件」という形に化けて**、原因を探せなくなります。

判断の出どころは取り込み定義の `OPTIONAL_TABLES`(取り込み元に
無くても失敗にしない表)で、別の一覧は作っていません。

### 最初の1行は、権限が無くても入れられます

ここを資材モードで塞ぐと、資材モードに入るための最初の1行を
どこからも入れられなくなります。**登録が1行でもあれば、その時点で
閉まります**(従来どおりの動き)。

### 現場に起きること

**今までの操作は変わりません。** アクセス権限を登録していない端末は
これまでどおり現場モードだけで動きます。登録すると、帯のモード切替に
資材モードが出ます(全部が効くのは開き直してからです)。

## VER2.5.3

**書き方が少し違うだけで固定適合を取りこぼしていたのを直しました。**
拾ったことは**黙らずに知らせます**。

### 何が起きていたか

移植元の `NormalizeKey` は `Select Case` の評価順の都合で、
半角小文字 `x` と全角 `Ｘ`/`ｘ` が「×」ではなく半角大文字 `X` に
なっていました。そのため

```
業界「5X10」 → 5×10  … 固定表に当たる
業界「5x10」 → 5X10  … 当たらない(段階表からの計算に落ちる)
```

と、**同じ寸法の書き方で結果が割れて**いました。

### そろえる4つ

1. 前後と**中の空白**を詰める(「5 × 10」も同じ鍵)
2. 全角の英数字を半角に、英字を大文字に
3. かけるとしか読めない記号(`×` `✕` `✖` `╳`)は `×` に
4. **数字に挟まれた** `X` `x` `Ｘ` `ｘ` `*` `＊` だけを `×` に

**4 で位置を見るのが要点です。** 挟まれていないものまで変えると、
`EXﾀｲﾄ`(実マスタに74行)が `E×ﾀｲﾄ` に、`EX2方向`(26行)が
`E×2方向` になります ── そこの X は EX受注 の X で「かける」では
ありません。固定表の鍵は `1×2` `4×8` `5×10` `4×10` `3×6` `5×8` と
**すべて数字に挟まれた形**なので、この規則で取りこぼしは出ません。

### 拾ったことを知らせます

そろえて初めて当たった行は、**管理番号と元の文字**を並べて出します。
選定は通りますが、マスタにゆれが残っていること自体は直したほうが
よい事実なので、両方を言います。

```
書き方をそろえて拾った行: 3件
  (選定は通ります。マスタ側をそろえておくと確実です)
  管理番号 1042  業界「5x10」→ 5×10
  管理番号 1088  記号「c8」→ C8
```

出る場所は2つです。

| どこ | いつ見えるか |
|---|---|
| 設定画面「いまの状態」 | **押さなくても見えます。** 件数と例を出し、要確認にします |
| 「適合範囲を再計算」の結果 | どの行かが全部出ます(10件まで。残りは件数を言って `app.log` へ) |

> 手元のマスタ(2,586行)で確かめたところ、固定表に当たる54行はすべて
> 正しい書き方で入っていたので、**この版で結果が変わる行はありません**。
> 取りこぼしを防ぐ備えと、ゆれに気づく手段です。

**パレットの「適合範囲を再計算」を、移植元と突き合わせて直しました。**

基準表に無い範囲ですが、現物の1900幅パレットの桁が7本だったことから

移植元は**空のときだけ埋めます**(補完)。現場が手で入れた本数を

> 取り込み元に値があればそれが入り、再計算は**空いているところだけ**を
> 埋めます。値そのものを直したいときは、取り込み元(またはマスタ管理)で
> 直してください。

いまの通り道は移植元と同じです。

```
範囲を決める(複合キー → 記号 → 業界 → 計算)

脚数・桁数を、空なら埋める
```

記号で当たった行だけは、表の値で**上書き**します(記号は現物の型
そのものなので、表のほうが確かな事実)。

原因は2つあり、どちらも「入れ替えたのに古いものが出る」を作ります。

### ① 画面のHTMLにキャッシュの指示が無かった

`/api/` にだけ「控えない」を付けていて、**画面のHTMLには指示が1つも
ありませんでした。** 指示が無いHTMLはブラウザが自分の判断で控えます

| | |
|---|---|
| 静的ファイル(CSS・JS) | **長く控えてよい。** URLに版が入っているので、入れ替えればURLが変わり必ず取り直される |
| それ以外(画面のHTML・API) | **控えない。** いま作ったものを毎回渡す |

でした。** 入れ替えたのに古いプロセスが残っていると、「すでに起動して
います」と答えて古いほうのブラウザを開くので、新しい版がいつまでも
動きません。

版が違えば**合流せず、古いほうを終わらせてから立て直します**。
ただし取り込みの途中なら止めません(中途半端なデータを残さない)ので、
そのときは理由をログに残して合流します。

### どのフォルダの、どの版が動いているか

設定画面の「この端末」に**アプリの置き場所**が出るようにしました。
版が古いときは、入れ替えたフォルダとここが同じかを確かめてください
(ショートカットの向き先が古いフォルダを指していることがあります)。
`GET /api/health` も `app_root` を返します。

- `docs/変更履歴.md` に節が無ければ試験が落ちる(従来どおり)

## VER2.2.1

**取り込みのたびに発注と入出庫履歴が倍になっていたのを直しました。**
入れ替えるだけで止まります。ただし**すでに増えた行は残る**ので、
下の手順で片付けてください。

自動取り込みが有効な端末では、**起動のたびに倍**になっていました。
開発用の写しでは 32件が 64件(中身が同じ重複62行)になっていました。

```
最初 3件 → 1回目 3件 → 2回目 6件 → 3回目 12件 …
```

取り込みは総入れ替えで、管理番号は手元で振り直されます。ところが
同期記録には**古い行ID**が残るので、取り込んだ行がどれも「まだ送って
いない」に見えます。次の取り込みはその前に書き戻しを走らせるので、
**取り込み元から来た行を新しい行としてもう一度**送っていました。
送信IDは送るたびに振り直されるため、一意索引の重複防止も効きません。

- 取り込んだ直後に、そのテーブルの行を**送信済みとして記録し直す**
  ようにしました。取り込んだ行は取り込み元から来たものなので、
  送り返す必要がありません
- 古い記録は消します。番号が振り直されたあとの古い行IDは**別の行**を
  指すので、残すと今度は**新しく登録した発注が「送信済み」に化けて
  二度と送られなくなります**(こちらのほうが気づけません)
- **こちらで出した発注はちゃんと送られます。** 増やさないために
  送らなくなる、では意味がありません(試験で固定しました)

### すでに増えてしまった行の片付け方

**順番が大事です。** 増えた行は取り込み元だけでなく、**各端末の手元にも
写っています**。入れ替えた直後の1回目の取り込みで、その手元の分が
取り込み元へもう一度送られます(そこで止まります)。なので、
**全部の端末が1回ずつ取り込んでから**片付けます。

1. **全端末を入れ替える。** 古い版が1台でも動いていると、また増えます
2. **各端末で1回ずつ取り込む**(起動すれば自動で走ります)。
   ここで最後の1回ぶんが送られ、以後は増えません
3. **数える。** どこか1台から。数えるだけなら安全です

   ```bat
   python scripts\dedupe_writeback.py
   ```
   ```
   対象: \\…\梱包資材マスタ.sqlite3
     資材パレット注文管理: 64件 → 重複 62件
     パレット入出庫履歴: 12件 → 重複なし
   ```

4. **消す。** `--fix` を付けます。**消す前に、同じフォルダへ丸ごと控えを
   取ります**(`梱包資材マスタ.bak-20260809103000.sqlite3`)。
   管理番号と送信IDを除いた全部の列が一致する行を重複とみなし、
   **いちばん小さい管理番号だけを残します**

   ```bat
   python scripts\dedupe_writeback.py --fix
   ```

5. **もう一度、各端末で取り込む。** 手元を、片付けたあとの取り込み元に
   合わせます

> 手順2を飛ばして先に消すと、手元に残っていた分が次の取り込みで
> また送られ、消したはずの行が戻ります。

## VER2.2.0

**共有フォルダのマスタが「sqlite3 として読めません」になるのを直しました。**
既存の手順は変わりません。

仕掛台帳(SIKA*)は読めるのにマスタだけ読めない、という形で出ていました。
同じフォルダ・同じ経路なので、違いは**そのファイルがどう作られたか**
だけです。原因は2つ重なっていました。

1. **開けたかどうかを確かめていませんでした。**
   `sqlite3.connect()` はファイルを触りません。開けたつもりのまま
   返ってきて、最初の問い合わせで初めて落ちます。そのため
   「別の開き方を試す」逃げ道が**一度も動いていませんでした**
2. **落ちた理由を捨てていました。** 画面には
   「sqlite3 として読めません」としか出ず、**なぜかが分かりません**

直したこと:

- 開くところで1文引いて、**引けたら開けた**と決めるようにしました。
  これで手を変えられます ── `URI(読み取り専用)` →
  `素のパス` → `手元への写し` の順に試します
- **共有の上で開けないときは、手元へ写してから読みます。**
  WAL で作られた sqlite3 は共有フォルダの上では開けません(共有メモリが
  要るため)。写せば読めるので、読むたびに写します。`-wal` / `-shm` も
  一緒に写すので、直前に書かれた分が抜けることもありません
  (書き戻しは写しへ逃がしません。書いたものがどこにも残らないため)
- **開けなかったときは、分かったことを全部出します。**
  大きさ・先頭の印・付き添いファイル・試した順と、それぞれの理由。
  そして次にすること(「変換したPCで `PRAGMA journal_mode=DELETE;` を
  実行して置き直してください」など)
- ふだんの開き方で通らなかったときは、動いていても「開き方」の行が
  出ます ── 写しながら動いているのは遅いので、黙っていません

**置き場所の指定が2通りになりました。**

| 書き方 | 例 | どこを見るか |
|---|---|---|
| 絶対 | `\\サーバ\共有\…` / `C:\data\…` | そのまま |
| 相対 | `data\src` / `..\共有` | **アプリのフォルダ**から |

相対の起点を「いまの作業フォルダ」にしないのが要点です。作業フォルダは
どこから起動したかで変わるので、同じ設定でも端末ごとに違う場所を
指すことになります。アプリのフォルダなら、**フォルダごとコピーして
配る運用でも写しの中の同じ場所**を指し続けます。
相対で書くと、その下に**実際の行き先**が出ます。

- 「参照…」で**ファイルを押しても選べる**ようになりました。目当ての
  ファイルが見えているのに「フォルダを選べ」と言われるのは一手多い
  ── 押すとその入れ物が入り、押したファイルに印が付きます
- 「参照…」の欄は相対でも開けます(どこから見た相対かは1か所で
  決まっているので、断る理由がありません)

## VER2.0.0

**資材選択の手順が変わりました。事前に周知してください。**

決まっていく順は「ロットを選ぶ → 製品サイズが入る → それが載る
パレットが決まる」です。パレットは製品のために選ぶもので、
画面もその順に直しました。以前は パレット → 製品 の順に2枚のカードが
並んでいて、**まだ分からないものを先に決めさせ**、あとから
「載るかどうか」を確かめる形になっていました。

| | 以前 | いま |
|---|---|---|
| 押す回数 | 3回(行を選ぶ → 適用 → セット) | **1回** |
| 順番 | 間違えると断られる(セットはパレットの後) | 順番は無い |
| 候補の一覧 | 別のカードにあり、畳まれていることがある | 同じカードの中に見えている |

- 「製品サイズ」と「パレットサイズ」の2枚を**1枚**にまとめ、
  題を「**パレットを決める**」にしました
- 「パレット検索」と「セット」は「**パレットを選ぶ**」1つになりました。
  載るパレットを探し、載ることを確かめ、両方を確定するところまで
  1回で行います
- **一覧の行を押した時点で決まります**(適用もセットも要りません)
- 一覧に無い寸法を使う道は残してあります(「一覧に無い寸法を使う」を開く)

**確かめる規則は1つも変えていません。** 載らないパレットを選べば
今までどおり断られます(`apply_product_size`)。押す回数を減らしただけです。

その他:

- 利用者設定(`data/user_config.json`)を追跡対象から外しました。
  端末ごとの上書きで、追跡していると**開発用に向けた一時パスが
  配布物に入ります**。取り込み元の既定は `packaging_tool/config.py`
  にある本番の共有フォルダです

## VER1.0.0

VBA + Access からの移行が一巡し、現場で使う7画面がそろった最初の版です。

**画面**

- ロット検索 / 資材選択 / 簡易在庫 / 倉庫連携 / 棚検索 / 選定ログ / 設定
- 結果は左、操作は右。**縦に長い面はタブで畳む**ので、操作の面は
  スクロールしません(設計指針 §4.2)
- 画面の移動で再読込しません。外枠(帯・レール)は残したまま
  `<main>` だけを差し替えます
- 押してから返るまでの手ごたえ ── 250ms を超えたら押したボタンが
  待機の姿になり、1.2秒を超えたら経過秒が付きます。数十秒かかる処理は
  帯に出るので、画面を離れても追えます

**業務**

- 選定・配置・描画計画は VBA からの移植のまま。41通りのゴールデンと
  1バイト単位で突き合わせています(`scripts/compare_ui.py`)
- 取り込み元は sqlite3。起動時に更新されたファイルだけを読み直します
- 発注と入出庫は登録のたびに取り込み元へ自動で送ります

**基盤**

- ダブルクリックする入り口は `Start.vbs` の1つだけ。現場モードか
  資材モードかは `アクセス権限` マスタが端末ごとに決めます
- 多重起動の防止、安全な停止、起動待機画面、長時間処理の監視
- 配色は `tokens.css` ただ1つが出どころ。351組のコントラストを
  機械で検査しています(`scripts/check_contrast.py`)
