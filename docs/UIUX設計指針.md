# UI/UX 設計指針 — 認知心理学・情報アーキテクチャ・色彩調和論

画面の見た目と操作を決めるときに従う原理と、それを本ツールへ適用した結果です。
**「なんとなく今風」ではなく、理由を説明できる設計**にすることが目的です。

「旧版」と書いてあるのは Excel VBA / tkinter 時代の画面です。配色や配置の
判断は**そこから引き継いだもの**が多く、なぜそうしたかを残してあります
── 現場が覚えている対応を、理由も分からず変えないためです。

- アーキテクチャと API → [`設計.md`](設計.md)

---

## 0. なぜこの3つか

| 観点 | 答えるべき問い | この画面での具体例 |
|---|---|---|
| **認知心理学** | 人は速く・正しく操作できるか | 「倉庫送信が押せない」理由に気づけるか |
| **情報アーキテクチャ** | 探しているものがどこにあるか分かるか | 「なぜこのパレットが落ちたか」をどこで見るか |
| **色彩調和論** | 見て分かるか。並べて美しいか | 7分類の色が本当に7つに見えるか |

3つは独立ではありません。**色は認知の入力**であり、**情報構造は探索の地図**です。
本ツールは VBA 時代から「認知心理学: 一貫した間隔定数(ゲシュタルト近接原則)」という
コメントを持っており、この設計思想は**新しく持ち込むものではなく、引き継ぐもの**です。

## 1. 認知心理学

### 1.1 ゲシュタルトの要因 — 「群」をどう見せるか

| 要因 | 適用 | 具体値・実装 |
|---|---|---|
| **近接** (proximity) | 関係するものを近づけ、無関係なものを離す | 8pxグリッド。要素間 8px / セクション内 12px / セクション間 24px。VBAの `secGap = 6` を8pxグリッドへ移植 |
| **類同** (similarity) | 同じ種類の操作は同じ見た目にする | 「操作の種類=色」の約束(§3)。加えて**同じトーン**に揃える |
| **閉合** (closure) | 枠で囲むと1つの群として知覚される | カードの1px罫線。`ttk.LabelFrame` の役割を継承 |
| **連続** (continuity) | 並んだものは同じ流れとして読まれる | 左レールの縦一列 = 作業の流れ。ボタン列の縦並び = 実行順 |
| **共通運命** (common fate) | **同期して変化するものは同じ群と知覚される** | **配置図のボードと選定リストの行を相互ハイライト**。「この行がこの板」という対応を、覚えずに見て分かるようにする |

共通運命の要因は旧版に無かったものです。tkinter Canvas ではヒットテストを自作する必要が
あり実装されていませんでしたが、SVG では各ボードが要素なので自然に実現できます。
**いまの画面で増える操作は、この1つに絞ります**(増やしすぎない)。

#### 近接の適用例 — ロット情報の12項目

VBA `capLot` は12項目を等間隔に縦一列に並べていました。並び自体は
「用途 → 製造寸法 → オーダー寸法 → 設備コース」という意味のある順序ですが、
等間隔に置くと **「板厚」と「オーダー板厚」の区別が見た目に現れません**。
取り違えると資材が1サイズずれます。

そこで**順序は変えず**、区切りだけを入れました。

| まとまり | 項目数 | 中身 |
|---|---|---|
| 品目 | 4 | 用途コード / 用途名 / 製造材質 / 製造調質 |
| 製造寸法(BOXコースなら **BOX実績寸法**) | 3 | 板厚 / 板幅 / 板丈 |
| オーダー寸法 | 3 | オーダー板厚 / オーダー板幅 / オーダー板丈 |
| 設備コース | 2 | 設計_設備コース / 実績_設備コース |

いずれも4以下で、§1.4 の作業記憶の上限に収まります。まとまりの見出し語は
VBAのキャプションから作っており、新しい業務語は増やしていません(§2.2)。

### 1.2 フィッツの法則 — 押しやすさは距離と大きさで決まる

```
T = a + b · log₂(2D / W)      T:所要時間  D:距離  W:目標の幅
```

| 適用 | 決定 |
|---|---|
| 目標を大きくする | ボタンの当たり判定を **最小 44×44px**(旧版 約90×24px)。タッチ端末があるため、マウス基準ではなく指基準で決める |
| 距離を縮める | 「在庫を見る」(旧パレットMAP)は**パレットの段の見出し**に置く(参照するデータの近くに操作を置く)。VBA の「フィッツの法則: 関連ボタンを横並びグループ化」というコメントを継承。段の中(`.pad`)に置かないのは、決まった段が畳まれて届かなくなるため ── **確定値が残る場所に操作も残す** |
| 画面端は実質無限の幅を持つ | **「終了」を右上端、「ライン切替」を上端**に置く。端に吸い付くので狙わずに押せる |
| **逆用: 押されたくないものは端に置かない** | **「倉庫送信」は端に置かない**。取り消せない確定操作なので、狙って押す必要がある位置に留める。管理者エリアも同じ理由で右下に隔離し、「認証」の手前だけ間隔を倍にする(VBA の `'少し離して誤操作防止'` を継承) |

### 1.3 ヒックの法則 — 選択肢が増えると遅くなる

```
RT = a + b · log₂(n + 1)      n:選択肢の数
```

資材選択画面には現在 **16個のボタン**があります。全部を同時に見せると
選択に時間がかかり、どれが「いま押すべきもの」か分かりません。

**解決は「隠す」ではなく「段階的開示 + 状態による強調」です。**

| 状態 | 見え方 |
|---|---|
| パレット未確定 | ①パレットのカードが開いている。②以降は畳まれ、1行の要約になる |
| パレット確定 | ①が要約行に畳まれ、②製品サイズが開く |
| 製品確定 | ③ボード選定が開き、「ボード選定」ボタンが**主動作**として強調される |
| 選定済み | 「ボード配置」が主動作になる |

- 畳まれたカードは**1行の要約(確定値)を必ず残す**ので、「何が決まっているか」は失われません
- **無効なボタンは消さず、無効のまま理由を添えます**。消すとレイアウトが動き、
  手が位置を覚えられなくなります(旧版の設計判断を継承)

> 旧版の「操作パネルを ①/② の2ページに分ける」という回避策は、
> ヒックの法則の観点では**正しい方向**でした。ただしページの切れ目が固定なので、
> 作業段階と一致しないことがあります。いまの画面は**段階に連動して開閉**することで、
> 同じ効果を自動で得ます。

### 1.4 作業記憶 — 覚えさせない

短期記憶に保持できる情報のまとまりは、古典的には 7±2、近年の推定では **4±1** とされます。
本ツールの作業では、常に次の4つを前提として保持する必要があります。

```
Lot番号 / パレットサイズ / 製品サイズ / いまのモード
```

これが**ちょうど4つ**であることを踏まえ、**ステータスリボンに常時表示**します。
5つ目以降(板厚・拠点・ライン)は同じ帯に置きますが、優先度を下げた表示にします。

旧版は「未設定」帯・モード帯・使用保護材ラベルが3か所に分散しており、
画面を移動すると見えなくなります。**設計目標は「覚えなくてよい」ことです。**

### 1.5 認識は再生に勝る (recognition over recall)

| 旧版 | いまの画面 |
|---|---|
| 発注コードを一覧から選ばないと倉庫送信できない(が、その理由は押すまで分からない) | ボタンの下に常時「発注コードと単位は一覧で選んだ行から取ります」と表示。押す前に分かる |
| 拠点をコンボボックスから選ぶ | 維持(選択肢が3つなので一覧が最適) |
| 背景画像は PNG/GIF のみ、と手順書で覚える | ファイル選択時にブラウザが対応形式を示す。JPEGも通る |

### 1.6 自然な対応づけ (natural mapping)

現実の配置と画面の配置を一致させます。**旧版の設計をそのまま維持します。**

```
現実:  アングル(上)                画面:  【アングル配置】  ← 一番上
       上用ボード                        【上用ボード配置】
       製品                              
       下用ボード                        【下用ボード配置】  ← 一番下
       パレット
```

同様に、選定リストも上用が上・下用が下に並びます。
**この順序を入れ替えることは、仕様変更にあたります。**

### 1.7 エラーの予防 (Norman)

| 種類 | 例 | 対策 |
|---|---|---|
| **スリップ**(意図は正しいが操作を誤る) | 「保存」を押すつもりで「セットクリア」を押す | 旧版は両方 `#ffc8c8` で**同じ色**。いまの画面は同じ赤のまま**濃い塗り(保存)と淡い塗り(取消)**で分ける |
| **ミステイク**(意図そのものが誤り) | 前のラインの選定結果のまま次のラインの発注を送る | **ライン切替時に未確定の選定があれば確認し、明示的にクリアする** |
| **強制機能** (forcing function) | 実績パターンの誤保存 | 認証するまで保存ボタンが押せない(旧版を継承) |
| **制約** (constraint) | 寸法欄に文字が入る | 数値入力のみ受け付ける。単位(mm)を欄に添える |
| **可逆性** | 「クリア」を押してしまった | 直後のトーストから1回だけ取り消せる |
| **確認は取り消せない操作だけ** | 確認ダイアログの慣れによる素通り | モーダルは倉庫送信・発注取消・確認済み化・ライン切替に限定。それ以外はトースト |

## 2. 情報アーキテクチャ

Rosenfeld / Morville の4体系(組織化・ラベリング・ナビゲーション・検索)で整理します。

### 2.1 組織化体系 — 何を基準に並べるか

情報の並べ方は原理的に5通り(LATCH: Location / Alphabet / Time / Category / Hierarchy)。
本ツールは **Time(=作業の順序)** を主軸にします。

```
① ロット検索 → ② 資材選択 → ③ 簡易在庫 → ④ 倉庫連携 → ⑤ 棚検索 → ⑥ 選定ログ → ⑦ 設定
   引く          決める         調べる       送る          取りに行く    確かめる     整える
```

これは旧版のタブ順と同一で、VBA の `mpMain.Pages` に遡ります。
**番号を振るのは装飾ではなく、この順序が実在するからです。**
(順序の無いものに 01/02/03 を振ると、あるはずのない意味を生んでしまいます)

さらに上位で3段階に束ねると、初めて触る人にも全体像が伝わります。

| 段階 | 画面 |
|---|---|
| **引く** | ① ロット検索 |
| **決める** | ② 資材選択 (③ 簡易在庫 / ⑤ 棚検索 は決める途中で参照する) |
| **出す** | ④ 倉庫連携 / 印刷 (⑥ 選定ログ / ⑦ 設定 は裏方) |

### 2.2 ラベリング体系 — 現場の言葉を使う

**システムの都合で言葉を作り変えません。**

| 使う言葉(現場語彙) | 使わない言葉 |
|---|---|
| 資材展開 / セット / 適用 | 展開実行 / 確定 / Apply |
| 疲労度優先 | 最適化オプション |
| 2山積 / 在庫考慮 | スタックモード / 在庫フィルタ |
| 倉庫送信 | 発注データ登録 |
| ▲薄 | 在庫僅少 |

旧版の文言は VBA から一貫して使われており、現場が既に覚えています。
**言い換えは学習コストの純増**なので行いません。
唯一足すのは「押せない理由」の説明文で、これは新しい概念ではなく既存の制約の説明です。

### 2.3 ナビゲーション体系 — 4種類を区別する

| 種類 | 実装 | 例 |
|---|---|---|
| **グローバル** | 左の縦レール(常時表示) | 7画面 |
| **ローカル** | 画面内のカード見出し | 【パレットサイズ】【製品サイズ】… |
| **コンテキスト** | 作業の流れに沿った横移動 | 「在庫を見る」→簡易在庫 / 「置き場をまとめて見る」→棚検索 / 「資材展開」→資材選択 |
| **補助** | 問題が起きたときの導線 | 候補0件のときの「選定ログを見る」/ マスタ未取込のときの「設定画面へ」 |

コンテキストナビゲーションは**旧版の重要な資産**です。
`btnUFMAP_Click` / `btnMap_Click` は単なる画面遷移ではなく、
**いま持っているデータを渡して移動する**ため、遷移先で入力し直す必要がありません。
いまの画面でもこの性質(データを持って移る)を維持します(設計.md §5.6)。

渡し方には3つの決めごとがあります。

1. **渡すのはサーバの作業状態だけ。** 画面から品目や寸法を送らせません
   ── 送らせると、同じ事実が画面とサーバの2か所に生まれます
2. **渡ってきていなければ、受け側のボタンを出しません。** 押せるのに
   何も起きないボタンは、壊れているのか使い方が違うのか区別できません
3. **渡された結果は、渡された理由と一緒に出します。** 打っていないのに
   欄が埋まっていると、前の人の打ち残しに見えます
   (簡易在庫の「資材選択で決めたパレットの寸法で引いています」)

**どの種類でも、移動で画面は作り直しません**(`app/static/js/nav.js`)。
白紙が挟まると、出したばかりのトーストが消え、接続断の帯が瞬き、
押した場所が作り直されます ── 速さの話ではなく、**同じ画面の中に居る
という感覚**が切れることが問題です(§1.4)。SPA にはしていません。
仕組みと制約は `docs/設計.md` §2。

### 2.3.5 入口は1つにする — ロット検索の作り直し

**同じことをする入口が2つあると、利用者はどちらが正しいかを判断しなければ
なりません。** その判断には情報が要り、情報は画面に書いていない ── これは
利用者の仕事ではなく、設計の失敗です。

ロット検索は VBA のフォームをそのまま引き継いだ形で、こうなっていました。

```
[一覧を検索] ← 上          結果が縦に伸びる ↓
一覧 ─────────           打つ → スクロールして読む → 戻って打ち直す
[LotNo を打つ] ← 下
ロット情報 / 引当 / 受注 / 図面
```

問題は2つです。

1. **入口が2つ**(一覧の検索欄と LotNo 欄)。番号を知っているときに
   どちらへ打つのが正しいかは、画面のどこにも書いていない
2. **入力と結果が上下に離れている**。打つ場所は下、結果はさらに下。
   1件見るたびに視線と手が往復する

作り直した形:

```
[ロットを探す]  ← 主入力。画面でいちばん大きい入力欄はこれ1つだけ
[絞り込み: チップ]
一覧 ────────  ← 縦に動くのはここだけ
   ↓ ダブルクリック / Enter
モーダル(前面に重ねる。閉じれば一覧がそのまま残る)
```

| 変えたこと | 理由 |
|---|---|
| LotNo 欄を消し、検索欄に一本化 | 7桁を打てば必ず1件になるので、**速い道は塞いでいない**。入口が1つなら迷わない |
| 1件に絞れたら自動で確定して開く | 旧版の「7桁で自動検索」と同じ体験を、入口1つで実現する |
| 結果をモーダルへ | 入力(上)と結果(下)を行き来させない。閉じれば元の一覧に戻るので、次の行をすぐ開ける |
| 読む順序はそのまま | ロット情報 → 試験指示票 → 引当 → 受注。**画面の作りは変えても、読む順序は仕様** |

> **モーダルを使ってよい条件。** §1.7 で「モーダルは取り消せない操作だけ」と
> しています。ここは**読むためのモーダル**で、閉じても何も失いません。
> 確認を求めるモーダル(倉庫送信など)とは別物として扱います。

### 2.3.6 全画面に同じ形を当てる — 結果は左、操作は右

VBAのフォームは1本の列に「入力 → 結果 → また入力」と積まれていました。
移植でその形をそのまま引き継いだため、**結果が入力のあいだに挟まる**
画面が4つ残っていました。

| 画面 | 以前の並び(1列) | 起きること |
|---|---|---|
| 資材選択 | パレット → 製品 → ボード → **配置図** → 上用 → 下用 → アングル → 出す | 図を見るには操作を全部通り過ぎ、直すには戻る |
| 簡易在庫 | 検索 → (図 \| 一覧) → **受け入れ / 払い出し** | 払い出しの対象は上の一覧で選んだ行なのに、欄はさらに下 |
| 棚検索 | 検索 → **配置図** → 置き場の中身 | 条件を変えるたびに図を通り過ぎて戻る |
| 倉庫連携 | **新規発注(12項目)** → 一覧 | 送った結果を見るには毎回フォームを通り過ぎる |

4つとも §4.2 が既に定めている形へ寄せました。

```
┌ 結果(スクロールしてよい) ─┬─ 操作(スクロールさせない) ┐
│  図・一覧・選んだものの中身  │  上から作業順。次の一手を強調  │
└────────────────┴─────────────────┘
```

**1列に積まないことが要点**で、左右に分ければ「入力しながら結果を見て
いられる」状態が自動的に成立します。列幅は画面ごとに変えます
(棚検索は図が主役なので 1.45:1、倉庫連携はフォームが12項目あるので 1.25:1)。

1列のままにした画面もあります ── **選定ログ**(結果しか無い)、
**設定**(順に読む)、**ロット検索**(§2.3.5 のとおりモーダルで解いた)。
分ける理由が無いのに分けると、片側が空いて落ち着きません。

> この形が崩れたことは**目で見ないと気づけない**ので、
> `tests/test_screen_layout.py` が構造を機械で見ています
> (結果カードが結果カラムに居るか / 操作カラムに `overflow: hidden` が
> 掛かっているか)。

#### 資材選択の16個のボタン — 段にして1つだけ強調する

§1.3 で決めていた段階的開示を、ここで実装しました。

- 操作カラムは **① パレット → ② 製品サイズ → ③ ボード → ④ アングル →
  ⑤ 出す** の5段。**順序・番号・要約・いまどの段かはサーバが決めます**
  (`presenters/selection.py` の `_apply_steps`)。画面側で「パレットが
  決まったか」を組み立て直すと、条件が2か所に分かれて必ず古くなります
- **開くのはいまの段だけ。** 5段すべてを開くと 1,489px になり、
  FHD 100%(894px)でも入りきりません。畳んだ段は確定値を1行残すので
  「何が決まっているか」は失われず、見出しを押せば開きます
- **強調するボタンは常に1つ**(`primary_action`)。16個が同じ重さで
  並ぶと、押すべきものを毎回探すことになります(ヒックの法則)
- 管理者エリアは既定で畳みます。日常操作ではありません(§1.2)

> **§4.3 の「860px以上なら全カード展開」は、1列だったころの話です。**
> 2カラムにして操作カラムを分けたいま、展開の可否を決めるのは高さでは
> なく**作業段階**です(§1.3 が本来そう書いていました)。

### 2.4 情報の匂い (information scent)

「その先に何があるか」を、行く前に示します。

| 場所 | 匂いの出し方 |
|---|---|
| 左レール | 各画面にバッジ。「済」「配置」「12」(選定ログの新着件数) |
| パレット一覧 | EX対象行に色。行を選ぶと単位・コードを即表示 |
| ボード候補 | 「▲薄」で在庫薄を予告 |
| 実行ボタン | 押した結果が変わる場合はラベルが変わる(疲労度ON時「疲労考慮ボード」) |

### 2.5 「なぜ」を追える構造

本ツール特有の要件として、**結果だけでなく理由が要る**という性質があります
(「なぜこのパレットが落ちたのか」)。

そこで選定ログを、独立した画面(⑥)であると同時に、
**資材選択画面の配置図の直下に直近5行を常設**します。
理由は結果のすぐ隣にあるべきで、別画面へ探しに行かせるものではありません。
全文は⑥で見ます。

## 3. 色彩調和論

### 3.1 旧版配色の診断 — なぜ7分類が3〜4段階にしか見えないのか

旧版の12色を測ると、原因が明確に出ます。

| | 色相 (H) | 明度 (L\*) |
|---|---|---|
| 旧版のボタン12色 | **0°〜273° に分散** | **76.0〜95.5(幅 19.4)に集中** |

つまり旧版は、色相を大きく散らしているのに、
**トーン(明度・彩度の組み合わせ)は全色が「ペールトーン」で固定**されています。
PCCS でいえば全色が `p`(pale)トーンの**ドミナントトーン配色**です。

ドミナントトーン配色は「まとまりの良さ」を得るための技法で、それ自体は正しい手法です。
しかし本ツールでは:

1. **地(`#dcdcdc`, L\*≈88)も同じ明度帯にある** → ボタンが地から浮かない(実測 1.00〜1.39:1)
2. **色相だけが弁別の手がかりになる** → 隣接色相(印刷32° / 切断依頼22° / ボード選定33°)が区別できない
3. **淡い色は色相の知覚差が小さい** → 彩度が低いほど色相の弁別能は落ちる

**結論: 手がかりを色相1本に集中させたことが原因**です。

### 3.2 解決 — トーンで「面」を分け、色相で「カテゴリ」を分ける

情報を2つの平面に分け、**平面はトーンで、平面内の分類は色相で**表します。

| 平面 | 役割 | トーン | 実測 L\* |
|---|---|---|---|
| **操作** | ボタン。前に出る | 濃色(dp/dk 相当)+ 白文字 | **31.9〜46.9** |
| **データ** | 配置図のボード面・状態帯。後ろに退く | 淡色(p/ltg 相当)+ 黒文字 | **81.5〜95.7** |
| **地** | ページ・カード | 無彩色に近い低彩度 | **95.0〜100** |

操作(L\*≈40)とデータ・地(L\*≈90)の間に **ΔL\* 約50** の断層ができるため、
「押せるもの」と「見るもの」が色相を判別する前に分かれます。
これは前注意的処理(pre-attentive processing)で処理される差で、探す必要がありません。

### 3.3 色相環上の配置

操作の色相は旧版の意味をそのまま継承します(**現場が覚えている対応を変えない**)。

| 操作 | 色相 | 由来 |
|---|---|---|
| 取消・保存 | 357° 赤 | 旧版 `#ffc8c8` |
| 印刷 | 15° 赤橙 | 旧版 `#ffdcb4` |
| 選定 | 26° 橙 | 旧版 `#ffe6c8` |
| 画面遷移 | 86° 黄緑 | 旧版 `#99cc00` |
| 検索・トグルON | 143° 緑 | 旧版 `#ccffcc` / `#90ee90` |
| 実行 | 214° 青 | 旧版 `#b4dcff` |
| 疲労度 | 273° 紫 | 旧版 `#b464ff` |

**色相を変えずにトーンだけを変える**ので、「橙っぽいのが印刷」という現場の記憶が
そのまま通用します。変わるのは濃さだけです。

#### 3.3.0 骨格の色は操作の色から独立させる

画面の骨格 —— 上の帯・いま居る場所・焦点・選択行・開いている面 —— は
**ティール**(`--accent`)で、操作の7色とは別の系統にしてあります。

以前は骨格の色が実行ボタンと同じ青でした。「押せるもの」と「いま見ている
場所」が同じ色で主張し合い、どちらの意味で青いのかが読み取れません。
系統を分けると、**青い塗りは実行だけを意味する**ようになります。

この色と造形は社内の SymfoNavi Data Hub に合わせています。同じ現場で
並べて使うものが別々の見た目だと、操作を覚え直すことになるためです。
合わせたのは次の5つで、業務の意味を持つ色(資材・図・保管位置)は
こちらの都合を優先して据え置いています。

| 合わせたもの | 中身 |
|---|---|
| 上の帯 | 濃紺→ティールのグラデーション。白文字。右に統一寸法の操作 |
| 骨格のアクセント | ティール(`#0b6d86` / 暗いテーマは `#5cc2d4`) |
| 影 | 広く淡く青みを帯びた影(`0 5px 18px` の 5%) |
| ボタン | 濃い塗り=起こす / 淡い塗り=参照・消す / 中立=主役でない |
| 焦点 | 太い淡い輪(3px)+ 輪郭の色が変わる、の二重 |

#### 3.3.1 1つの組に見えるまで揃える

色相を継承したうえで、**明度をそろえ、彩度を 15% 落として**あります
(OKLCh で L=0.47 / C×0.85。暗いテーマは L=0.70 / C×0.82)。

以前は色ごとに個別に濃度を決めていたため、明度が 0.44〜0.56 とばらつき、
彩度も色相ごとの上限近くにありました。1つずつ見れば正しくても、
**7色が横に並ぶと「絵の具の箱」に見え、どれが主役か分からなくなります。**
明度がそろうと、色相の違いだけが残って1つの組に見えます。

資材・配置図・保管位置の色は**情報そのもの**なので触っていません。
騒がしさの出どころは操作の色と罫線で、そこだけを直せば足ります。

### 3.4 データの色 — 補色対を維持する

上用=赤(357°) / 下用=緑(143°) は**色相差 153°、ほぼ補色**です。
これは対比が最大になる正しい選択であり、**維持します**。

ただし実測で問題が見つかりました。

```
見出し  上用 #b4232a (L*39.7) / 下用 #1f7a4d (L*45.3)  → ΔL* =  5.6
面      上用 #f7d9da (L*89.1) / 下用 #d7ecdf (L*91.6)  → ΔL* =  2.4
```

**赤と緑は、P型(1型)・D型(2型)色覚で最も弁別しにくい組み合わせ**です。
明度差がほぼ無いため、色相を知覚できない場合に区別する手がかりが残りません。

**対策(3重化)**

| 手がかり | 対策 |
|---|---|
| 明度 | 面 上用 `#f2c9cc` (L\*84.5) / 下用 `#e8f6ed` (L\*95.7) → **ΔL\* 11.2**<br>見出し 上用 `#b4232a` (L\*39.7) / 下用 `#125334` (L\*30.8) → **ΔL\* 8.9**(白地比も 5.32→9.08 に改善) |
| 位置 | 上用は必ず上、下用は必ず下(§1.6) |
| 文言 | 【上用ボード配置】/【下用ボード配置】を常に併記 |

色を一切知覚できなくても、位置と文言で確実に区別できる状態を担保します。

### 3.5 構造の色とデータの色を分ける

アクセント(青 214°)は**構造**にだけ使います。選択行・フォーカスリング・リンク・
現在地の表示です。

実測すると、アクセント青とアングルの青緑(175°)は **色相差 39°**、
アングルと下用の緑(143°)は **32°** と近接しています。狭い帯域に3つ入っています。
そこで**使い方の規則**で衝突を防ぎます。

> **アクセント青は面に使わない。アングルの青緑は構造に使わない。**

同じ帯域の色でも、片方が「1〜2pxの線と小さな印」、もう片方が「見出しと図の面」であれば、
面積とトーンが違うため混同しません。**色相の距離だけで解こうとせず、
役割の分離で解きます。**

### 3.6 面積比 — 60:30:10

| 比率 | 対象 | 色 |
|---|---|---|
| **60%** | 地(ページ・カード) | 無彩色に近い低彩度(`#eef1f5` / `#ffffff`) |
| **30%** | データ面(配置図・表) | 淡色(上用・下用・アングル) |
| **10%** | 操作 | 濃色(ボタン)+ アクセント |

彩度の高い色を10%に抑えることで、**操作が目に飛び込みます**。
旧版は淡色とはいえ画面の広い面積にボタン色が敷かれており、
「どこも同じくらい主張している」状態でした。

### 3.7 地の色を選ぶ

純白(`#ffffff`)一色にせず、ページの地を **`#eef1f5`(色相214° / 彩度25.9% / L\*95.0)**
にします。

- アクセント青と**同じ色相**にわずかに寄せた無彩色に近いグレー。
  無関係な灰色ではなく「選ばれた灰色」になる
- 白いカードが地から浮くので、カードの境界が罫線に依存しない
- 窓際端末では純白の輝度が眩しく、長時間の作業で疲れる

### 3.8 工場環境への対応

| 条件 | 対策 |
|---|---|
| 高天井照明・粉塵で色が沈む | 彩度に依存せず、**明度差 ΔL\* 30以上**を分類の主手がかりにする |
| 斜めから見る液晶(視野角で明度が変わる) | 文字コントラストを AA(4.5:1)ではなく**実質 6:1 以上**で設計(§トークン表は 5.02〜14.66) |
| 手袋・汚れた指 | 当たり判定 44px(§1.2) |
| 夜勤・暗い倉庫 | ダークテーマを用意。`prefers-color-scheme` を尊重しつつ手動切替も可能にし、設定を保存する |
| 色覚特性 | 色は**必ず第2の手がかり(形・位置・文言)と併用**する。単独では使わない |

## 4. レイアウト — FHD(1920×1080)で設計する

### 4.1 使える高さ

**現場端末はすべて FHD(1920×1080)** です。ただし Windows の表示スケールで
CSSピクセルの視野が変わるため、実際に使える高さはスケール次第で1.7倍違います。

```
1920 × 1080(物理)
  ÷ 表示スケール                  → CSSピクセルの視野
  − Edge のタブバー + アドレスバー   約 90px
  − Windows のタスクバー            約 48px
  = innerHeight
  − ステータスリボン                   48px
  = 本体に使える高さ
```

ブラウザ枠とタスクバーはOSと一緒に拡大するので、**CSSピクセルで見た高さは
スケールが変わってもほぼ一定**です。したがって視野の縮小分がそのまま効きます。

| 表示スケール | CSS視野 | `innerHeight` | 本体の高さ | 同時に開けるカード |
|---|---|---|---|---|
| **100%** ← **現場はこれ** | 1920×1080 | 約 942px | **約 894px** | 3〜4枚(ほぼ全部) |
| 125% | 1536×864 | 約 726px | **約 678px** | 2枚 |
| 150% | 1280×720 | 約 582px | **約 534px** | 1枚 |

> **確認済み(2026-08)**: 現場端末は FHD・表示スケール **100%**。
> 設計はこの行を基準にします。

**約894px 使えるので、当初の目的だった「操作パネルの ①/② ページ分割を
やめて同時に見せる」が素直に成立します。** これが今回の刷新でいちばん
効く一点です(VBAは1024×768前提で作られており、①②の分割はその名残)。

ただし**125% / 150% でも壊れない**ようには作ります。理由は3つ:

1. 端末が入れ替わったときに設計をやり直さなくてよい
2. 見えにくいと感じた利用者が自分でスケールを上げられる(アクセシビリティ)
3. Edge の「ズーム」も同じ効き方をする(Ctrl+マウスホイールで簡単に変わる)

`layout.css` の高さ方向の分岐(560px / 860px)はそのために置いてあり、
100%では常に一番広い段に入ります。

#### 測り方(端末が変わったとき)

Edge のアドレスバーに `about:blank` を入れ、`F12` のコンソールで:

```js
innerWidth + "×" + innerHeight + " / DPR " + devicePixelRatio
```

`devicePixelRatio` が 1 なら 100%、1.25 なら 125%、1.5 なら 150% です。

### 4.2 スクロールの規則

旧版の手順書は「画面はスクロールしない。一覧の中だけがスクロールする」と定めています。
いまの画面ではこれを**役割ごとに分けて**継承します。

| 領域 | スクロール | 理由 |
|---|---|---|
| ページ全体 | **しない** | 現在地を見失う |
| 操作カラム | **しない** | 見えていない操作に気づけない。手が位置を覚えられない。→ 収まらない分は**段階的開示**(§1.3)と**面**(§4.2.1)で解く |
| 結果カラム(配置図) | **する** | 図は連続した1つの対象。見るものであって探すものではない |
| 一覧(表)の中 | **する** | 旧版どおり。最低10行を表示 |

**「操作はスクロールさせない / 結果はスクロールしてよい」**という区別が、
旧版の原則を、表示スケールの大きい端末でも成立させる鍵です。

基準は FHD 100%(本体 894px)です。**それより低い画面では、操作カラムも
スクロールさせます**(`layout.css` の `@media (max-height: 820px)`)。
隠すより動かせるほうがましだからで、消えた操作には気づけませんが、
スクロールバーは「まだ下がある」と言ってくれます。

いまの実測(1920×942 / 明暗どちらのテーマでも同じ):

| 画面 | 残っているスクロール |
|---|---|
| ロット検索 | 一覧の中(200行) |
| 資材選択 | **無し** |
| 簡易在庫 | 保管位置の図(拡大するため) |
| 倉庫連携 | **無し** |
| 棚検索 | 配置図(同上) |
| 選定ログ | **無し** |
| 設定 | 取り込み結果の本文 |

どれも枠の決まった箱の中で、ページも操作カラムも動きません。

#### 4.2.1 面(タブ)— スクロールの代わりに分ける

縦に積んだものは、下にあるほど「無いもの」として扱われます。
スクロールしないと見えないということは、**見えていないあいだは存在を
思い出せない**ということで(§1.4)、面に分ければ中身を隠しても
**見出しは常に見えます**。

面に分けてよいのは次のときだけです。

- **択一のもの**(受け入れ / 払い出し)── 同時にはしない
- **同じ問いへの別の答え方**(配置図 / 選定一覧)── 見比べるより、
  片方を大きく見たい
- **縦に積むと枠に入らないもの**(設定の6面。積むと 1,612px はみ出した)

逆に、面が守らなければならないことが4つあります。

1. **問題を隠さない。** 中身に「足りません」があるタブは、開いていなくても
   見出しがそう言う(`presenters/settings.py` の `tab_badges`)。
   隠したせいで気づけなくなるなら、スクロールのほうがまだまし
2. **その先に何があるかを示す**(情報の匂い、§2.4)。件数や状態を見出しに添える
3. **色だけで伝えない**(§3.8)。選ばれている面は下線と太字でも分かる
4. **押した結果がその面にあるなら、こちらから開く。** 図の置き場を押したら
   「置き場の中身」へ、一覧の行を押したら「配置図」へ移る ──
   **押したのに何も起きないように見えるのが一番わるい**

並び・見出し・状態はサーバが決めた値を写すだけで、
「いまどの面を見ているか」だけを画面が持ちます(業務の事実ではないため)。

### 4.3 段階の切り替え

**高さで分岐します**(この画面が不足するのは横ではなく縦だからです)。
`@media (min-height: ...)` を使います。

**開閉を決めるのは高さではなく作業段階です**(§1.3 / §2.3.6)。
1列だったころは高さで段階を切っていましたが、2カラムにして操作カラムを
分けたいま、操作側に入る量は表示スケールにほとんど依存しません
── 5段すべてを開けば 1,489px で、100%(894px)でも入りきりません。

| 本体の高さ | 対応するFHDの表示スケール | 見え方 |
|---|---|---|
| 860px〜 | **100%(現場はこれ)** | 図を大きく。操作は**いまの段だけ**開く |
| 〜860px | 125% / 150% | 同じ。図が縮み、結果カラムがスクロールする |

畳まれたカードは**確定値の1行要約を必ず残す**ので、どの段階でも
「何が決まっているか」は失われません。見出しを押せば開きます。

### 4.4 グリッドと寸法

| 項目 | 値 |
|---|---|
| 基本グリッド | 8px |
| 本文 | 15px / 行間 1.65 |
| 一覧 | 14px / 行高 28px |
| 寸法・数量 | **等幅 + `font-variant-numeric: tabular-nums`** |
| 最小当たり判定 | 44 × 44px |
| カラム比 | 結果 : 操作 = 1.3 : 1 |
| 角丸 | カード 10px / ボタン・入力 7px / 小箱 6px / 丸 999px |
| 太さ | 400 · 600 · 700 の3段だけ |

#### 4.4.0 画面は「暗い帯1本 + 紙2枚」

```
┌────────────────────────────────────────┐
│ 濃紺→ティールの帯   Lot・パレット・製品・拠点 / モード / 終了 │  56px
├──────────┬─────────────────────────────┤
│ レール    │ 本体                          │
│ (紙1枚)  │ (紙1枚。中で結果|操作に割る)   │
└──────────┴─────────────────────────────┘
```

**暗い帯を1本だけ通します。** 明るい面ばかりだと、どこが枠でどこが中身かが
面積でしか分からず、画面全体がのっぺりします。上に濃い帯があると、
下の作業面は明るく広く見えます。

帯の左端はアプリの**持ち主**を示す場所です。名前と版のバッジ(`VER1.0.0`)を
置き、**どの画面を開いても変えません。** 端末はフォルダごとコピーして配るので、
「その端末に入っているのはどれか」を電話で聞かれることがあります ── 画面を
見れば答えられる場所が1つ要ります。バッジは小さく静かに(10px・等幅)しますが、
消したり畳んだりはしません。聞かれるのは稀でも、聞かれたときに無いと困ります。

帯の上の部品(モード切替・終了)は**うっすら白を重ねるだけ**で作り、
枠線も別の色も足しません。寸法は `--ctl-h` / `--ctl-r` の1組に統一します
── 高さも角の丸みもばらばらだと、まとまりとして読めません。

**紙は2枚まで。** レールと本体が対等な2枚で、その中で更にカードを囲むと
「箱の中の箱の中の箱」になります。面(タブ)の中に1枚だけ置くカードは
枠も影も外し、本体と同じ紙の続きにします。囲んだままにするのは、
**並べて比べるカード**(設定の状態4枚)と、**沈んだ地の上に置くカード**
(操作の列)だけです。

レールの1項目は2行 —— 太字の名前と、小さな説明。名前だけでは「倉庫連携」が
何をする画面なのかは押すまで分かりません(情報の匂い、§2.4)。
説明の文言はサーバが持ちます(`shell.NavItem.note`)。

#### 4.4.1 境目は線ではなく、面と影で作る

罫線を濃くするほど画面は**「区画の集まり」に見えて、中身より枠が目に付きます。**
以前は `--rule` が 1.53:1 あり、カード・表・入力欄・タブの下地が
すべて同じ濃さの線で囲まれていました。区切りは足りていたのに、
どこを見ればよいかは分からない状態です。

いまの分け方は3つで、**強い順に使い分けます。**

| 手段 | どこに使うか |
|---|---|
| **面の明度差** | 役割が違うとき(結果=`--surface` / 操作=`--sunken`) |
| **淡い輪郭 + 薄い影** | 同じ役割のものを並べるとき(カード) |
| **余白だけ** | 数が少なく、近接で読めるとき(リボンの4項目) |

線が要るのは**中身がスクロールして見出しの下から生えてくる**ときだけです
(設定画面の状態カード)。そこだけ見出しに罫線を戻します。

太さの段は 400 / 600 / 700 の3つに限ります。段が多いほど
「どれが重要か」が伝わらなくなるためで、差を付けられるところは
大きさと色で付け、太さは**いま見るべきもの**に取っておきます。

小ラベルの総大文字 + 広い字間もやめました。日本語には大文字が無いので
効くのは "STEP 2" のような英数だけで、字間だけが間延びしていました。

**寸法を等幅・桁揃えにするのが、実務でいちばん効く改善です。**
可変幅では `1150` と `1180` の桁がずれ、一覧を縦に読むときに読み違えます。
本ツールは寸法の読み違いがそのまま資材の誤発注になるため、ここは譲れません。

#### 4.4.2 機械が吐いたものは暗い面に置く

取り込みの結果・ログ・図面の中身は、**人が書いた文ではなく機械の出力**です。
明るい紙の上に等幅で並べると、周りの説明文と同じ重さに見えて、
「読むもの」と「確かめるもの」の区別が付きません。

暗い面(`--night`)に等幅で落とすと、そこだけ性質が違うことが一目で分かり、
本文の側も読みやすくなります。行の種別(警告・失敗・成功)は
**左端の3pxの色帯**で示し、色だけに頼らないよう文字も添えます。

高さは頭打ちにします(結果の写しは9行、ログは面の残り)。伸ばすと
**下にある操作ボタンが押せる場所から追い出される**ためで、あふれた分は
その中で動かします(§4.2 の「一覧の中は動いてよい」)。

#### 4.4.3 列の多い一覧は主従に畳む

倉庫連携の発注一覧は15列あります。等しく並べると1列 40px しか無く、
品名も納入先も読めないうえ、**どれが行の名前なのかも決まりません。**

同じものの言い換えか付帯情報どうしを組にして、**太字の主**と
**小さい灰色の従**の2行に畳みます。事実は1つも減らず、列は8つになります。

```
管理番号 / 登録日時    LotNo / 品名      発注コード / 用途   厚 / 幅×丈
──────────────────────────────────────────────────────
8                     L6200J0           P-1100             3
2026-08-09 10:14      テスト品          H197               1100 × 2000
```

守ることが3つあります。

1. **畳む相手は同じものの言い換えか付帯情報だけ。** 「LotNo と品名」は
   同じ1本の材の呼び名ですが、「LotNo と納入先」は別々の事実です。
   見た目の都合で意味を混ぜません
2. **並べ替えに使う列は畳まない。** 畳んだ値には見出しを置けないので、
   並べ替えの手段が消えます。ロット一覧は8列とも並べ替えに使うので、
   そちらは畳まず、行の高さだけを 42px にそろえます
3. **どれを主にするかはサーバが決める**(`presenters/warehouse.ORDER_VIEW`)。
   画面は指図どおりに `values` から拾うだけで、事実の置き場所は1つです

行の高さを 42px にそろえるのは、**目が縦に走るとき、高さがまちまちだと
行を数えられない**ためです。ボタンの入る列だけは畳まず、幅を先に
確保します ── 文字は切れても読み返せますが、ボタンは切れたら押せません。

### 4.5 フォント

Webフォントは読み込みません。工場内LANはCDNに届かず、日本語フォントを
埋め込むと数MBになります。端末に必ずある書体を役割で使い分けます。

```css
--sans: system-ui, -apple-system, "Segoe UI", "Yu Gothic UI", "Meiryo UI",
        "Hiragino Sans", sans-serif;
--mono: ui-monospace, "SFMono-Regular", "Cascadia Mono", Consolas,
        "Yu Gothic UI", monospace;
```

#### 大きさは6段しか使わない

以前は 7 / 8 / 9 / 10 / 10.5 / 11 / 11.5 / 12 / 12.5 / 13 / 13.5 / 14 /
14.5 / 15 / 16 / 17 / 19 / 20px と **18種類**ありました。0.5px 違いは
並べても差として読めず、**揃っていないことだけが伝わります**。
6段に畳むと、大きさの違いが**役割の違い**として読めるようになります。

| 段 | 大きさ | 何に使うか |
|---|---|---|
| `--fs-2xs` | 10px | 見出しの上の小さな札・単位。読まなくてよいもの |
| `--fs-xs` | 11px | 表の見出し・添え字・状態のピル |
| `--fs-sm` | 12px | 表の中身・補足の一文。**いちばん多く使う** |
| `--fs-md` | 13px | 本文・ボタン・入力欄。既定 |
| `--fs-lg` | 15px | 数値の主役(寸法・件数)・カードの題 |
| `--fs-xl` | 19px | 画面の題。1画面に1つだけ |

**迷ったら1つ下へ。** 工場の画面は情報量が正義で、大きい字は場所を
食うだけのことが多いためです。

例外は2つだけ、いずれも「字」ではなく「形」です ── SVG の中の文字
(`viewBox` の利用者単位でCSSのpxではない)と、記号1文字の大きさ
(`.chip::before` の `●`、`.sortmark` の `▲`)。

#### 押すものと、読むものを分ける

| token | 値 | 何に |
|---|---|---|
| `--hit` | 44px | **押すものの最小**。ボタン・入力欄(§1.2) |
| `--row-h` | 26px | 表の行 |
| `--cell-x` / `--cell-y` | 8px / 3px | 表の升の余白 |
| `--gap` / `--gap-sm` | 10px / 6px | 並べるものの間 |

**表の行は 44px を割ってよい。** 行は「狙って押す的」ではなく、目で
追って選ぶものなので、読める範囲まで詰めてかまいません ── 一度に
見える行数のほうが、探す速さに効きます(仕掛一覧で 42px → 26px、
FHD で 9行 → 17行)。押す的である**ボタンと入力欄は 44px を保ちます**。

密度を変えるときに触るのはこの表だけです。1か所で決まっているので、
画面ごとに詰め具合が違う、が起きません。

### 4.6 待たせ方 — 動きで状態を伝える

静止画として正しくても、**押してから返るまでの数秒に何も言わない画面は
「効かなかった」と読まれます。** そして人はもう一度押し、同じ処理が2回走ります。

伝える場所は、近いところから順に増やします。

| 待ち時間 | どこに出すか | 何を出すか |
|---|---|---|
| 〜250ms | 何も出さない | 一瞬で終わるものに待機の姿を出すと、画面がちらつくだけ |
| 250ms〜 | **押したものそのもの**(`busy.js`) | 記号が回る輪に変わり、押せなくなる(二度押しを止める) |
| 1.2秒〜 | 同じボタンの中 | 経過秒。**何秒待っているかが分かれば、待てるかどうかを自分で決められる** |
| 数十秒〜 | **上の帯**(`running.js`) | 脈打つ点・名前・いまの段・経過・進み具合 |

待機の姿を出す口は1か所です ── `api.js` の送信そのものを捕まえて、
`busy.watchClicks()` が覚えている**いま押されたボタン**に出します。
画面を1つずつ書き換えなくても全部に効きます。

帯に出すのは、**取り込みが数分かかり、始めた画面を離れたくなる**からです。
離れたら終わったかどうかが分からない、では戻って確かめるしかなく、
そのあいだ元の作業が途切れます。何も走っていないときは丸ごと消します ──
ずっと居座る枠にすると、「動いていない」ことを読むために毎回そこを見ることになります。

段のある処理(19テーブルの取り込み)は、横棒1本では**どこで転んだかが
読めません。** 段ごとのカードを並べますが、**全部は並べません**
(§1.4 作業記憶は4±1)。出すのは6枚までで、選ぶ順は

1. 失敗した段 ── 必ず出す。隠すと直すべきものが見えなくなる
2. いま走っている段
3. 残りは新しいものから

通し番号は元の並びのまま(`17 / 19`)にして、詰め直しません。
並べきれなかった分は「ほか 13 件は完了しました」と数えて言います ──
**黙って落とすと「全部出ている」に見えます。**

動きはすべて `prefers-reduced-motion: reduce` で止まります。前庭障害の
ある人には、回転や脈動が不快や目眩の原因になるためです。動きは
**手がかりを増やすためのもの**で、それだけが頼りになる場所は作りません。

#### いちばん長い待ちは、起動そのもの

上の表は「押してから返るまで」の話ですが、**押す前にいちばん待たされる
のは起動**です。ここには前提が1つあります ── **待たせるために見せる
ものが、待たせている当のものより後に出てはいけない。**

以前はアプリ本体を組み立ててからブラウザを開いていたので、待機画面が
出るころには待つ理由がほぼ終わっていました。出る意味がありません。
いまは待ち受けを先に始め、待機画面だけを出してブラウザを開き、本体は
そのあとで差し替えます(設計.md §2.5)。実測 **約 0.15 秒**。

出すものにも同じ理屈が要ります。

| 決めごと | なぜ |
|---|---|
| 外部への要求を1つも出さない | CSS を別に取りに行くと、その1往復ぶん遅れる。1回で出す |
| 帯と同じ濃紺〜ティールの地に置く | 起動直後に出るものが本体と地続きに見える。**別のアプリが開いたと受け取られない** |
| 段は横に4つ | 開く前に**全体の長さ**が見える。縦に積むと、いくつあるのか下まで見ないと分からない |
| 割合が分からないあいだは往復する帯 | 止まっていないことは示すが、**進み具合を偽らない**。取り込みが実際の割合を返したら、そちらに切り替える |
| 待たずに入る道を置く | 取り込みが終わっていなくても画面は使える。**待たせきりにしない** |
| 失敗したら理由とログの場所をその場に出す | 出ないと、次に何をすればよいのかがどこにも無い |

## 5. タッチ対応(マウスが基準、タッチも通る)

タッチ専用UIは作りません。**マウス用のUIが、そのままタッチでも破綻しない**ようにします。

| 項目 | 対応 |
|---|---|
| 当たり判定 | 44×44px 以上(マウスでも押しやすくなるので損がない) |
| ホバー | **ホバーでしか出ない情報を作らない**。ツールチップは補足のみで、必須情報は常時表示 |
| 右クリック | 使わない。すべての操作は左クリック(タップ)で到達できる |
| ドラッグ | マップ編集のみ。Pointer Events で統一し、マウス・タッチ・ペンを同じコードで扱う |
| ダブルクリック | **仕掛一覧の「行を開く」だけ**。必ず Enter でも同じことができる(下記) |
| スクロール | 慣性スクロールを妨げない。`touch-action` を明示 |
| 入力欄 | 数値欄は `inputmode="numeric"` でテンキーを出す |

> **ダブルクリックを1か所だけ認めた理由。** もともと「使わない」と
> 決めていました。発見しにくく、タッチでは打ちにくいためです。
> 仕掛一覧では利用者の指定で採り、次の3つを条件にしています。
>
> 1. **唯一の道にしない。** 行にフォーカスして **Enter** でも開く。
>    上下キーで行を移れる
> 2. **見えるところに書く。** 一覧の見出しに常時「行をダブルクリック
>    (またはEnter)で詳細を開きます」(文言はサーバが持つ)
> 3. **1回押しは選ぶだけ**にする。押しながら一覧を目で追うことがあるので、
>    開くのは意図した操作のときだけ ── 逆に言えば、ここでダブルクリックを
>    使うのは「選ぶ」と「開く」を分けたいからです

## 6. 設計チェックリスト

新しい画面・部品を作るときに確認します。

### 認知
- [ ] いま何が決まっているかが、画面を移動しても見えるか
- [ ] 押せないボタンに、押せない理由が書いてあるか
- [ ] 取り消せない操作が、端や導線上に置かれていないか
- [ ] 覚えておかないと次の操作ができない情報が無いか
- [ ] 現実の配置(上用が上)と画面の配置が一致しているか

### 情報構造
- [ ] 現場の言葉を使っているか(システム語彙に言い換えていないか)
- [ ] 結果だけでなく理由に辿り着けるか
- [ ] 画面を移るとき、いま持っているデータが引き継がれるか
- [ ] 行く前に「その先に何があるか」が分かるか

### 色
- [ ] その色は**トーン**で平面(操作/データ/地)を示しているか
- [ ] 色相は旧版の意味と一致しているか(勝手に変えていないか)
- [ ] 色を知覚できなくても、形・位置・文言で区別できるか
- [ ] 文字 4.5:1 / 部品の輪郭 3:1 を満たすか(`scripts/check_contrast.py` が検査)
- [ ] アクセント青を面に使っていないか

### レイアウト
- [ ] FHD × 表示スケール150%(本体 約534px)に収まるか
- [ ] 操作カラムがスクロールしていないか
- [ ] 寸法・数量が等幅・桁揃えか
- [ ] 当たり判定が 44×44px 以上か
- [ ] ホバーでしか出ない必須情報が無いか
- [ ] 列の多い一覧で、行の高さがそろっているか(§4.4.3)
- [ ] 畳んだ列に、並べ替えに使うものが混じっていないか

### 手ごたえ
- [ ] 1秒を超えうる操作に、押したものの上で待機の姿が出るか(§4.6)
- [ ] 数十秒かかる処理が、画面を離れても帯で追えるか
- [ ] 段のある処理で、失敗した段が必ず見えるか
- [ ] 出しきれなかったものを、数えて言っているか
- [ ] `prefers-reduced-motion: reduce` で動きが止まるか
- [ ] 動きだけが頼りになっている手がかりが無いか
