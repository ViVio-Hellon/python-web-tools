# デスクトップ版(Tauri)の作り

VER4.0.0 から、ブラウザで開く代わりに**専用の窓(exe)**で動かせるようになりました。
**ポートを使いません。** ブラウザ版(`Start.vbs`)もそのまま残してあり、予備として使えます。

## 何が何をするか(各言語が得意なことをする)

```
梱包資材総合ツール.exe(Rust / Tauri)        … src-tauri/
 ├─ 窓(WebView2)・帳票の窓・終了の確認・多重起動の防止
 ├─ Python を子として起動・監視(落ちたら理由の画面)
 └─ 画面の要求(app://…)を受けて、Python の標準入力へ渡す
        │ 標準入出力(1件 = 見出し1行 + 本文)
        ▼
bridge.py(Python)                             … ポート無しの入口
 └─ Flask アプリを WSGI として呼ぶだけ(待ち受けない)
        ▼
app/・packaging_tool/(Python)                 … 業務の計算・取り込み・画面の組み立て(変わらず)
app/static/js(JS)                             … 画面の操作(変わらず。窓まわりだけ desktop.js)
```

| 担当 | 理由 |
|---|---|
| **Rust**: 窓・起動・終了・多重起動・Python の監視 | OS の窓とプロセスを扱うのが得意。exe 1つで配れる |
| **Python**: 選定・配置・取り込み・書き戻し・画面 | 実測で重い処理は無い(自動選定・配置 約45ms)。VBA と同じ結果を守る試験 3,000件余りがこの形で書かれている。書き直す利点が無く、危険だけがある |
| **JS**: 画面の操作 | 今までどおり。デスクトップ版のときだけ、別窓・社内サイト・帳票の「閉じる」を外枠に頼む |

## ポートを使わない仕組み

- 画面は独自の宛先 `app://localhost/`(Windows の WebView2 では `http://app.localhost/`)を読む。
  これは**ネットワークを通らない**(外枠の中で受ける名前)
- 外枠はその要求を Python の標準入力へ渡し、標準出力から応答を受け取る(`src-tauri/src/bridge.rs` と `bridge.py`)
- 起動トークン・Host の確認・画面の取り合いの確認など、アプリ側の守りはそのまま生きている
- 試験で確かめていること:
  - `tests/test_bridge.py`: ソケットを開くと落ちるようにして Python を起動しても、画面・操作・終了が通る
  - `scripts/desktop_smoke.py`: exe を本当に起動し、exe・Python・WebView の**どのプロセスもポートで待ち受けていない**

## 動きの約束

| 場面 | 動き |
|---|---|
| 起動 | 窓がすぐ出て「起動しています」→ Python の待機画面(取り込みの進み具合)→ 業務画面 |
| もう1つ起動しようとした | 新しく起動せず、開いている窓を前に出す(OS のファイルロックでも止める) |
| 窓の × / 画面の「終了」 | 保存していない配置図・実行中の取り込みがあれば訊く(ブラウザ版の「終了」と同じ確認) |
| 帳票(Lot印刷・切断依頼・配置図印刷) | 別の窓で開く。「印刷する」で印刷ダイアログ、「閉じる」でその窓だけ閉じる |
| 社内の閲覧システムへのリンク | 既定のブラウザで開く(アプリの窓では開かない) |
| Python が見つからない・起動できない | 理由と次にすること(Python の入れ方・pip の打ち方)・ログの場所を窓に出す |
| Python が途中で落ちた | 窓を読み直して理由の画面を出す |
| exe を止めた | 標準入力が閉じるので Python も終わる(取り残さない) |

Python は**同梱しません**。各PCに入っている Python を使います(`python.exe` → `py.exe -3` の順に探す。
`PACKAGING_TOOL_PYTHON` で指定もできる)。必要なパッケージは Flask だけです(waitress はブラウザ版用)。

## 作り方

**Windows 版は GitHub Actions が作ります**(`.github/workflows/desktop-windows.yml`)。
押すたびに、Python の試験・Rust の試験・exe の作成・exe を起動しての確認まで流れ、
成果物 `PackagingTool-windows` に `PackagingTool.exe` が入ります。

配るとき:

1. 成果物から `PackagingTool.exe` を取ってきて、ツールのフォルダの**直下**に置く
2. `scripts\make_dist.bat` を流す(`梱包資材総合ツール.exe` の名前で配布フォルダに入る)

手元で作るとき(開発機):

```
cd src-tauri
cargo build --release            # target/release/PackagingTool(.exe)
python ../scripts/desktop_smoke.py --exe target/release/PackagingTool    # Linux は xvfb-run を前に付ける
```

Linux で作るには WebKitGTK が要ります(`libwebkit2gtk-4.1-dev` など)。

## 置き場所の決まり

- exe は `bridge.py` と同じフォルダに置く(上の階層もたどるので、`src-tauri/target/...` から動かしても見つかる)。
  `PACKAGING_TOOL_ROOT` で指定もできる
- 版は `config/app.json`・`src-tauri/tauri.conf.json`・`src-tauri/Cargo.toml` の3か所。食い違うと試験が落ちる
- アイコンは `scripts/make_desktop_icon.py` で作る(`src-tauri/icons/`)

## 確かめきれていないこと(Windows の実機で見る)

この版の確認は、Linux(WebKitGTK)の上で窓を実際に動かして行いました。Windows では
GitHub Actions が「起動して画面が届く・待ち受けない・止めたら Python も終わる」まで確かめます。
次は**実機で人が見る**必要があります:

- 窓の × で、保存していない配置図があるときの確認ダイアログ
- 帳票の「印刷する」から実際に紙が出ること(WebView2 の印刷ダイアログ)
- 「表を持ってくる」のドラッグ&ドロップ
- 取り込みの記録の「保存」(ファイルのダウンロード)
- 社内の閲覧システムのリンクが既定のブラウザで開くこと
