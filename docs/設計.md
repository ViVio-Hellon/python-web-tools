画面は Flask + HTML/CSS/JS、業務ロジックは Python、データは SQLite。
元は Excel VBA + Access のツールで、業務判断は VBA の移植です。

## 1. 守っている約束

破ると必ず事故になるので、**違反はバグとして扱います**。

1. **業務判断はすべて Python**。JS が持つのは「ビューモデル → DOM/SVG」の
   純関数だけ。二重に持つと、テストの無い側に分裂する
2. **APIは更新後のビューモデル一式を返す**(差分ではない)。この規模
   (数KB)で差分を使う利点は無く、画面側の不整合バグの温床になる
3. **HTTPステータスで断りの種類を分ける**
   - `400` 入力の形が違う。**サーバの状態は動いていない**
   - `422` 形は正しいが業務として断る
   - `403` その操作をする資格が無い
   - `409` 別の誰かが先に変えていた
4. **断りの種類は `reason` 定数で運ぶ**。文言から推し量らない
   ── 文言を直した日に区別が壊れる
5. **同じ事実を2か所に持たない**。持つと必ずどちらかが古くなる
6. **一覧に無いものは選べない**。画面で絞るだけでなくサーバでも確かめる
7. **色だけで意味を運ばない**。色の出どころは `tokens.css` ただ1つ
8. **選定・配置・描画計画のアルゴリズムは1行も変えない**
   (`board_selection_algorithm` / `placement_algorithm` /
   `placement_render` / `angle_render`)。変えるときはゴールデンを
   作り直し、なぜ変えたかを残す

## 2. 構成

```
Start.vbs ─▶ start_app.py ─▶ launch_guard.py ─▶ server.py (waitress)
  (通常)       (環境確認)      (多重起動判定)      │
                                                   ├─ boot_server (待機画面だけ) ─▶ ブラウザ
                                                   └─ 差し替え ─▶ app/ (Flask)
start.bat ─▶ 同じ経路(コンソール表示・診断ログ詳細)
stop.bat  ─▶ process_manager.py ─▶ POST /api/shutdown → 応答が無ければPIDで停止
画面を閉じる ─▶ 心拍が途切れる ─▶ idle_exit ─▶ 同じ停止の道
```

```
  ブラウザ                app/templates/*.html   画面の骨格(Jinja2)
                          app/static/js/         描画と入力(ESモジュール)
                          app/static/css/        tokens.css が色の唯一の出どころ
        │ fetch / JSON(同一オリジン)
  ─────▼──────────────────────────────────────────────
  app/routes/             Blueprint。入力の形だけ見て下へ渡す
  packaging_tool/presenters/   ビューモデルの組み立てと状態機械
  packaging_tool/*_session.py  画面をまたぐ作業状態(プロセスに1つ)
  packaging_tool/*_service.py  業務ロジック
  packaging_tool/*_algorithm.py 選定・配置(VBAからの移植。触らない)
  packaging_tool/db.py, source_db.py, data_sync.py, outbox_sync.py
  ─────┬──────────────────────────────────────────────
        ▼
   SQLite(手元)  +  sqlite3(共有・取り込み元/書き戻し先)
```

**SPA にしていません。** ルータ・状態管理・ビルド工程という3つの複雑さに
見合うものが、画面7つのこの規模では得られないためです。npm も webpack も
使わないので、社内端末では `pip install -r requirements.txt` だけで動きます。

**ただし画面の移動で再読込はしません**(`app/static/js/nav.js`)。
レールを押すと、行き先のHTMLをサーバから貰って `<main>` を差し替えます。
入れたのはこの1つだけで、上の3つは入れていません:

| SPA が抱えるもの | ここでは |
|---|---|
| クライアント側ルータ | 無い。**URLと行き先の対応はサーバが持つ** |
| クライアント側の状態管理 | 無い。画面が持つ事実は増えていない(§1 の規則5) |
| ビルド工程 (npm / webpack) | 無い。素の ES モジュールのまま |

差し替えるのは `<title>` / 画面ごとの `<style>` / リボン / レール /
`<main>` / 画面ごとの `<script>`。**残すのは接続断の帯とトーストと心拍**で、
これらは「いまこの瞬間の状態」を持っていて行き先とは関係がないためです。

リボンは差し替える側なので、**差し替えた直後に描き直すもの**があります ──
帯の「いま動いているもの」(`running.js`)がそれで、新しいリボンは空で
来るため `wireShell()` の中で今の状態を書き戻します。書き戻さないと、
移った先で「何も動いていない」ように見えます。

得るのは速さではなく、**同じ画面の中に居るという感覚**です。白紙が
挟まると、出したばかりのトーストが消え、接続断の帯が瞬き、押した場所が
作り直されます(設計指針 §1.4)。

守らなければならないことが2つあります。

1. **モジュールは使い回される。** 同じ画面へ戻ってきたとき `start()` が
   もう一度呼ばれるので、要素は毎回引き直し、モジュール変数は入り口で
   初期化する
2. **`document` / `window` の listener とタイマーは残る。** `nav.js` の
   `pageSignal()` / `onLeave()` に繋いで、画面を出るときに切る。切り忘れると
   別の画面に居るあいだも動き続け、戻るたびに1本増える

**モード切替だけは読み込み直します**(`app.js` の `wireMode`)。
出せる画面そのものが入れ替わるので、レールも権限も作り直させます。

取りに行けない・形が違う・古いブラウザ ── どの場合も `location.href` へ
落ちるので、**普通の遷移ができなくなることはありません。**

### 状態の置き場所

| 持ち物 | 置き場所 | なぜそこか |
|---|---|---|
| リボンに出る事実・画面間の受け渡し | `work_context` | 全画面が読む。DB接続を持たない外枠からも読める必要がある |
| 資材選択の作業(候補・モード・配置) | `selection_session` | 1画面の中で完結する |
| 棚検索の検索条件と編集中のマップ | `layout_session` | 同上 |
| 長時間処理の受け付けと進捗 | `jobs` | 画面を閉じても走り続ける |

どれも**プロセスに1つ**で、保存しません(落ちたら消える)。
1サーバ = 1セッションで、複数タブは同じ状態を共有します。

画面側にも1か所だけ「持ち物」があります。**走っている処理の写し**
(`app/static/js/jobs.js`)で、`GET /api/jobs` を叩くのはここだけです。
帯と設定画面の両方が要りますが、それぞれが叩くと**同じ事実を二か所で
持つ**ことになり、片方だけ古い、が起こります。見張りは1本にして、
欲しい側が `subscribe()` で受け取ります(間隔は走っていれば0.7秒、
何も無ければ15秒)。**判断は何もせず、返ってきたものを写すだけ**です。

`sqlite3` の接続はスレッドをまたげないので、**要求ごとに取り直し**、
セッションには `bind()` でその要求の接続を持たせます。

## 2.5 起動 ── 待機画面より前に、重いものを置かない

起動でいちばん時間を食うのは **Flask とアプリ本体の import** です。
以前はそれを済ませてからブラウザを開いていたので、待機画面が出るころには
待つ理由がほとんど終わっていました ── **待たせるために見せるものを、
待たせていた**ことになります。

```
ポートを決める → 待ち受け開始(待機画面だけ)→ ブラウザ
    → 本体を組み立てて差し替え → 重い初期化(取り込み)
```

最初の3つは標準ライブラリと `config/app.json` だけで済みます。
実測で **待機画面まで約 0.15 秒 / 準備完了まで約 0.6 秒**(手元の Linux。
起動のたびにログへ「待機画面まで N 秒」を残すので、端末ごとに測れます)。

| 決めごと | なぜ |
|---|---|
| 待機画面は `packaging_tool/boot_screen.py` が組み立てる | Flask を読み込む前に出す必要がある。**Jinja2 のテンプレートにできない** |
| 骨格は1つ。Flask 側の `/` も同じ関数を呼ぶ | 2枚持つと、直したほうと直していないほうが場面によって出る |
| 外部への要求を1つも出さない | CSS を別に取りに行くと、その分だけ遅れる。色は `tokens.css` を**読んで埋め込む**(出どころは1つのまま) |
| 待ち受けは開き直さない | `boot_server.Handover` が WSGI の呼び先を差し替える。開き直すと、その瞬間の問い合わせが落ちて「接続できません」に見える |
| モードを決めるのに `app` を読まない | `access_control.startup_grant()` を直接呼ぶ。Flask の import が待機画面より前に来ない |
| トークンは待ち受けの前に決める | 差し替えの前後で変わると、待機画面が持っているトークンが通らなくなる |
| 待機画面は `Cache-Control: no-store` | 控えが残ると、次に開いたときに居座る |

本体ができるまでのあいだ、業務の要求には **503 と「起動しています」** を
返します。404 にすると「無い」に見えます。

## 2.6 終了 ── 確実に終わる

**窓が無いアプリなので、タブを閉じたら終わったつもりになります。**
残っていると、次の起動が「すでに起動しています」と判定して古いほうの
ブラウザを開くので、**入れ替えた新しい版がいつまでも動きません**。

### 止めたのに終わらなかった理由

waitress の受付の輪は `while map:` で回ります。`server.close()` が閉じるのは
**待ち受けのソケットだけ**で、ブラウザが張っている keep-alive の接続は
map に残ります。つまり画面を開いたまま止めると、待ち受けは閉じるのに輪は
回り続け、プロセスが残ります。

3段で受け止めます。

1. `AppServer.stop()` が**残った接続も閉じる**(`wasyncore.close_all`)
2. `start_app._hold_until_stopped()` が待ちに**上限**(6秒)を置く
3. それでも終わらなければ `os._exit(0)`。止まらないことの害のほうが大きい

### 画面が居なくなったら終わる

`packaging_tool/idle_exit.py`。画面は 20 秒ごとに `POST /api/alive` を送り、
閉じたことは `sendBeacon` で即座に伝えます。

| | |
|---|---|
| 心拍が途切れてから | 90秒 |
| 閉じた合図を受けてから | 8秒(そのあいだに心拍が戻れば取り消し) |
| 処理中 | **落としません。** 取り込みの途中で終わるとDBが中途半端に残る |
| 1度も繋がっていない | 落としません。`--no-browser` の使い方を巻き添えにしない |

猶予を置くのは、**`pagehide` が再読込でも飛ぶ**からです。戻ってくれば
次の心拍で取り消されます。

止め方は `/api/shutdown` と同じ道(`AppServer.stop`)を通します ──
止め方が2つあると、片方だけ直した状態を作ります。
`/api/alive` は**トークンを要求しません**。要求すると、トークンが切れた
画面が黙って死んだ扱いになり、開いているのに終了してしまいます。

### 入れ替えたら、CSS と JS を取り直させる

配布はフォルダごとコピーなので、版が上がってもファイル名は変わりません。
ブラウザは同じ名前の控えを持っているので、場面によっては古い見た目のまま
になります。`app/__init__.py` の `_register_static_version()` が
`url_for('static', ...)` に `?v=<版>` を付けます。

版は `config/app.json` ただ1つが出どころなので、**上げ忘れなければ必ず
変わります**。上げ忘れは `tests/test_app_config.py` が捕まえます
(版に対応する節が `docs/変更履歴.md` に無ければ落ちる)。

## 3. セキュリティ

社内LANの端末で動く前提ですが、**同じPCの別プロセスや、利用者が偶然開いた
外部のWebページから叩かれない**ようにします。

| 対策 | 内容 |
|---|---|
| バインド先 | `127.0.0.1` のみ。LANからは届かず、ファイアウォール警告も出ない |
| 起動トークン | 起動ごとに `secrets.token_urlsafe(32)`。`/api/*` と `/report/*` に必須 |
| Host 検証 | `127.0.0.1:<port>` / `localhost:<port>` 以外は 400(DNSリバインディング対策) |
| 同一オリジン | `Sec-Fetch-Site` を確認。CORS ヘッダは一切返さない |
| 権限分離 | **権限の無いモードの Blueprint は登録しない**(404)。加えて、いまのモードも要求ごとに確かめる(403) |
| 管理者パスワード | 応答に載せない。認証したかの1ビットだけ返す |

> **守りを要求する経路は `app/__init__.py` の `TOKEN_REQUIRED_PREFIXES` が
> 決めます。** `/api/*` だけを見ていたころ、帳票の `/report/*` が素通しに
> なっていました(Lot番号・品名・板厚・寸法・梱包数が丸ごと入ります)。
> **業務データを返す経路を足したら、ここに入れること。**

> 権限分離は「ボタンを隠す」ではなく「**エンドポイントが無い**」で保証します。
> 画面の状態だけで守ると、要求を直接投げられたときに何も残りません。

## 3.5 アクセス権限とモード

### モードは2つ

| モード | 何をするか | 既定ポート |
|---|---|---|
| **現場** | ロットを引いて資材を選び、発注を出す | 8713 |
| **資材** | 受け取った発注を確認する(出す・取り消すのは現場) | 8723 |

定義の出どころは `packaging_tool/modes.py` ただ1つ。画面・権限・ポート・
ナビゲーションはすべてここを読みます。旧名 `warehouse` は `material` の
別名として受けるだけで(ショートカットと設定ファイルの互換)、
**新しく書くところには使いません**。

### 誰が何をできるか

`アクセス権限` マスタ(取り込み元の sqlite3 に置き、他のマスタと同じく
取り込む)が、**Windows のログインID と PC名**を条件に権限を与えます。

```
ログインID  PC名        権限            有効
yamada      (空)        mode:material   1     … 山田はどのPCでも資材
(空)        NLM-PC-042  mode:material   1     … この端末は誰でも資材
suzuki      NLM-PC-042  mode:material   1     … 鈴木がこの端末のときだけ
```

- 空欄は「問わない」。**両方が空の行は効かせません**(全員への許可に
  なって権限を設ける意味が消えるため)。書かれていれば設定画面が警告に出す
- 該当行の**和**を取ります。片方だけを採る規則にすると、どちらが勝つのかを
  覚えていないと結果を説明できません
- 大文字小文字は区別しません(Windows がそうなので)
- **該当が1行も無い端末は現場モードだけ。** 締め出さず、勝手に強い権限も
  渡しません。全部止めると取り込みの失敗で全員が仕事を始められなくなり、
  全部許すと登録し忘れた端末が資材モードに入れてしまいます

### 権限を増やすとき

`packaging_tool/access_control.py` の `permissions()` に足すだけです。
**マスタの表は変えません** ── 増えるのは「権限」列に入る値だけ。
知らないコードが書かれていたら、設定画面が「効いていない」と教えます。

### なぜ2段で守るのか

| 段 | 何を守るか | 通らないと |
|---|---|---|
| 登録しない | **誰か**(権限を持たない端末) | 404 |
| モードを確かめる | **いつか**(権限はあるが別のモードで作業中) | 403 |

**404 は「無い」、403 は「今はできない」。** 混ぜると、権限を足せば直るのか、
モードを切り替えれば直るのかが利用者に分かりません。

> **【以前との違い】** 現場と資材は別プロセス・別ポートで、資材専用の
> エンドポイントは資材ポートのサーバにしか登録していませんでした。
> 分かれていたのは「どのショートカットを押したか」であって**誰か**では
> なく、同じPCの別の人が資材のポートを開けば資材の操作ができました。
> いまは身元で分け、そのうえで画面から切り替えられます。
> ポートはモードごとに分けたまま(2つのモードを同時に開く場面があるため)。

> 権限を足しても、**登録済みのエンドポイントは開き直すまで増えません**。
> 起動時に権限が無くて登録しなかったものは 404 のままです(設定画面が
> そう案内します)。

## 4. API

- 参照は `GET`、状態を変えるものは `POST`
- エラーは HTTPステータス + `{"error":{"code":"...","message":"現場向けの日本語"}}`
- **文言はサーバが持つ**。画面ごとに言い回しが割れない

| メソッド | パス | 何をするか |
|---|---|---|
| `GET` | `/api/health` | 起動確認・生存監視 |
| `GET` | `/api/jobs` | 取り込み・書き戻しの状態 |
| `POST` | `/api/alive` | 画面の心拍。**トークン不要**(§2.6) |
| `POST` | `/api/shutdown` | 安全な停止 |
| `POST` | `/api/mode` | モードの切替。**権限のあるモードだけ**(無ければ403) |
| `GET` | `/api/lot/list` | 仕掛一覧(絞り込み後の画面ぜんぶ) |
| — | ↑ 一覧を返すもの全部 | **1件に絞れても確定しない**(開くのは開く操作のときだけ。VER4.8.7〜) |
| `POST` | `/api/lot/list/filter/add` `/remove` `/clear` | 条件チップの足し引き |
| `POST` | `/api/lot/list/search` `/sort` `/page-size` | 一覧検索・並べ替え・表示件数 |
| `GET` | `/api/lot/list/suggest?q=` | 打った文字から**足せる条件**を作る |
| `POST` | `/api/lot/list/saved/save` `/load` `/delete` | よく使う条件 |
| `GET` | `/api/lot/<lot_no>` | 1件開く。**包装仕様書の取得を裏で始める** |
| `POST` | `/api/lot/expand` | 資材展開(製造板幅・板丈を製品サイズへ) |
| `GET` | `/api/spec-sheet/<no>` `/image` | 包装仕様書の図面(状態 / 画像) |
| `POST` | `/api/spec-sheet/<no>/refresh` | 手元のものを捨てて取り直す |
| `GET` | `/api/selection/state` | 資材選択の画面全体 |
| `POST` | `/api/selection/pallet/apply` `/search` `/pick` | 適用 / 検索 / **一覧の行を覚える** |
| `POST` | `/api/selection/product/apply` | セット(回転すれば収まる場合は幅丈を入替) |
| `POST` | `/api/selection/clear` | セットクリア |
| `POST` | `/api/selection/board-type` | ボード種別の切替 |
| `POST` | `/api/selection/boards/auto-select` `/place` `/add` `/remove` `/clear` | ボード選定・配置・手動増減 |
| `POST` | `/api/selection/angles/auto` `/add` `/remove` `/draw` | アングル4操作 |
| `POST` | `/api/selection/toggle/<name>` | 全件表示 / EXのみ / 2山積 / 疲労度 / 在庫考慮 |
| `POST` | `/api/selection/1p0113/force` `/qty` | 裸梱包モードと乗数 |

## 5. ロット検索 ── 探す → 絞る → 見つける → 開く

**入口は検索欄1つ**です。番号を知っていれば打てば1件になり、知らなければ
「あの厚みの、あの用途のやつ」から絞れます。

```
探す(検索欄)→ 絞る(条件チップ)→ 見つける(一覧)→ 開く(モーダル)→ 次へ
```

### 入口を1つにした

以前は「一覧を検索する欄」と「ロット番号を打つ欄」が別にあり、番号を
知っているときにどちらへ打てばよいかを**利用者が判断していました**。
しかも番号の欄は一覧の**下**にあり、打つ場所と結果が上下に離れていて、
打つ → スクロールして読む → 戻って打ち直す、を繰り返すことになります。

いまは検索欄に打ち、打つたびに一覧を絞り込みます。**1件に絞れても勝手には開きません**
(VER4.8.7〜)。以前は1件になった時点でサーバが確定していましたが、7桁目を打つ前に
詳細へ移ってしまい、「有るかどうかだけ見たい」ができませんでした。しかも開くと作業中の
ロットが替わり、前のロットの製品サイズや倉庫送信の下書きが消えます。

> **規則はこれだけ: 開くのは、開く操作をしたときだけ。** 行のダブルクリック / Enter と、
> 検索欄で Enter(1件に絞れているとき)。絞り込みだけでは作業中のロットも変えません。

### 結果はモーダルに集める

詳細(ロット情報・試験指示票・引当・受注・包装仕様書の図面)は**前面に
重ねて**出します。縦に伸ばさないので、閉じれば元の一覧がそのまま残り、
次の行をすぐ開けます。**入力(上)と結果(下)を行き来させない**ための
作りです。

開く操作は**ダブルクリック / Enter**。1回押しは選ぶだけ ── 押しながら
一覧を目で追うことがあるので、開くのは意図した操作のときだけにします。
ダブルクリックは見ただけでは分からないので、一覧の見出しに常時
「行をダブルクリック(またはEnter)で詳細を開きます」と出します。

読む順序(ロット情報 → 試験指示票 → 引当 → 受注)は VBA のフレーム順の
ままです。**画面の作りは変えましたが、読む順序は仕様**です。

### 絞り込み

判断は `lot_query.py` が持ちます。

- **絞れる列 = 一覧に出ている列**。見えていない列で絞れると、なぜその
  件数になったのかが読めない。列を増やすときは `COLUMNS` に1行足せば、
  一覧・絞り込み・並べ替えのすべてに同時に効く
- **使える演算子は列の型が決める**。文字は `= / ≠ / 含む`、数値はこれに
  帯(`≥ ≤ > <`)が付く。画面で弾くだけでなくサーバでも確かめる
- **候補は実データから作る**。0件になる条件を勧めても意味がない
- **1ロット1行**。ロット番号は BOX工程ごとに複数行ありうるが、1件検索は
  先頭レコードしか見ないので一覧も同じ1行に揃える ── 揃えないと、
  押しても同じ内容が出る行が並ぶ
- **件数は切る前の数も言う**。「200件」とだけ出すと、それが全部なのか
  切られたのかが読めず、探し漏れに気づけない
- **0件のときは何をすればよいかまで言う**(条件を外す / 検索語を消す)

よく使う条件は名前を付けて `user_settings` に残します。押すと**いまの
条件に足します**(置き換えません)── 置き換えると、いま絞ってある内容が
黙って消えます。まっさらにしたいときは「全解除」があります。

## 5.4 資材選択 ── 決まっていく順に並べる

決まる順は1本の鎖です。

    ロットを選ぶ → 製品サイズが入る(製造板幅・板丈) → それが載るパレットが決まる

**パレットは製品のために選ぶもの**なので、製品が先です。以前は
「パレットサイズ」「製品サイズ」の2枚をこの逆順に並べていました。
まだ分からないものを先に決めさせ、あとから「載るかどうか」を確かめる
形で、押す回数も3回(行を選ぶ → 適用 → セット)必要でした。しかも
順番を間違えると断られます(「先にパレットサイズを設定してください」)。

いまは**1枚のカードで1回**です。

| | 以前 | いま |
|---|---|---|
| 押す回数 | 3回 | **1回** |
| 順番 | 間違えると断られる | 無い |
| 候補の一覧 | 別カード。畳まれていることがある | 同じカードの中 |

- 「パレットを選ぶ」… 載るパレットを探し(`auto_select_pallet`)、
  適用し、載ることを確かめて(`apply_product_size`)、両方を確定する
- **一覧の行を押した時点でも決まる。** 行を押すこと自体が
  「このパレットにする」という意思なので、そこまで済ませる
- 一覧に無い寸法を使う道は畳んで残す(§1.3 段階的開示)

**確かめる規則は1つも変えていません。** 載らないパレットを選べば
今までどおり断られます。押す回数を減らしただけです。

> 段を2つに分けなかったのは、**いまの段だけを開く**仕組み(§1.3)と
> 噛み合わないためです。分けると、候補の一覧が必要なときに畳まれます。

## 5.5 画面の骨格 ── 結果は左、操作は右

VBAのフォームは1本の列に「入力 → 結果 → また入力」と積まれていました。
移植でその形を引き継いだため、**結果が入力のあいだに挟まる**画面が
4つ残っていました(資材選択・簡易在庫・棚検索・倉庫連携)。

```
┌ 結果(スクロールしてよい) ─┬─ 操作(スクロールさせない) ┐
│  図・一覧・選んだものの中身  │  上から作業順。次の一手を強調  │
└────────────────┴─────────────────┘
```

1列のままにしたのは **選定ログ**(結果しか無い)・**設定**(順に読む)・
**ロット検索**(モーダルで解いた、§5)の3つです。

### 資材選択の段

操作カラムは5段(パレット → 製品サイズ → ボード → アングル → 出す)で、
**順序・番号・要約・いまどの段か・次に押すボタンはすべてサーバが決めます**
(`presenters/selection.py` の `_apply_steps`)。画面側で「パレットが
決まったか」を組み立て直すと、条件が2か所に分かれて必ず古くなります。

- **開くのはいまの段だけ。** 5段すべてを開くと 1,489px になり、
  FHD 100%(894px)でも入りきりません
- 畳んだ段は**確定値を1行残す**ので「何が決まっているか」は失われず、
  見出しを押せば開きます
- 強調するボタンは常に1つ(`primary_action`)

理由は [`UIUX設計指針.md`](UIUX設計指針.md) §2.3.6 に書いてあります。
形が崩れたことは目で見ないと気づけないので、
`tests/test_screen_layout.py` が構造を機械で見ています。

## 5.6 画面をまたぐ受け渡し ── ボードMAP / パレットMAP

選定したボードが5種類あるとき、置き場を1件ずつ探させると5回打ち直す
ことになります。旧版(`btnMap_Click` / `btnUFMAP_Click`)はここを1押しで
済ませ、**合計疲労度**まで出していました ── 「どれを取りに行くか」
ではなく「**全部でどれだけ歩くか**」が分かるのが要点です。

| 渡す口 | 受ける口 | 何が渡るか |
|---|---|---|
| `POST /api/selection/map` | `POST /api/layout/from-selection` | `work_context.map_items`(上用・下用・アングル) |
| `POST /api/selection/stock` | `presenters/inventory.initial()` | `work_context.stock_size`(確定パレットの寸法) |

**渡すのは `work_context` だけです。** 画面から品目や寸法を送らせません
── 送らせると、同じ事実が画面とサーバの2か所に生まれます(§1)。
渡す側は「押した」ことだけを伝え、受ける側は作業状態を読みます。

- 渡すものが無ければ **422**。移動もしません
  (`REFUSE_NO_HANDOFF`。要求の形は正しいので 400 ではありません)
- 受け側のボタンは、渡ってきていなければ**出しません**
  (`presenters/layout` の `handoff` が件数を返す)
- 置き場が登録されていない資材は**黙って落としません**。
  光らないぶんは合計にも入らないので、言わないと嘘になります
- 「在庫を見る」はパレットの**段の見出し**に置きます。段の中(`.pad`)に
  置くと、決まった段は畳まれるので届かなくなります ── 確定値が残るのは
  見出しなので、操作も見出しに置きます

## 8. 取り込み元と設定

### 取り込み元は sqlite3

梱包資材マスタと仕掛台帳は、共有フォルダに置かれた **sqlite3 ファイル**です
(`packaging_tool/source_db.py`)。手元の作業用DBとは別物なので、開き方も
扱いも分けます。

- **読むときは読み取り専用**(`file:...?mode=ro`)。取り込みのつもりで
  共有のファイルをうっかり書き換えない
- **開けたかどうかは、引けたかどうかで決める。** `sqlite3.connect()` は
  ファイルを触らないので、開けたつもりのまま返って最初の問い合わせで
  落ちる。開くところで1文引いて確かめてから返す ── そうしないと
  「別の開き方を試す」逃げ道が一度も動かない(現場で踏んだ)
- **開けるまで手を変える。** `URI(読み取り専用)` → `素のパス` →
  `手元への写し`。共有フォルダ(SMB)の上の sqlite3 は、WAL で作られて
  いると**読むだけでも開けない**(WAL は共有メモリを使い、SMB にはそれが
  無い)。写せば読めるので、`-wal` / `-shm` ごと写して読む。
  **書き戻しは写しへ逃がさない** ── 書いたものがどこにも残らない
- **開けなかった理由は捨てない。** `source_db.probe()` が、大きさ・
  先頭の印・付き添いファイル・試した順と理由を返し、設定画面が
  次にすることまで書く(「`PRAGMA journal_mode=DELETE;` を実行して
  置き直してください」)。「読めません」だけでは現場も私たちも直せない
- 拡張子は `.sqlite3` / `.db` の両方を見る。上流の付け方にこちらが折れる
- **列が無ければ言う。** 上流が列名を変えても `row.get()` は None を返すので、
  取り込みは「成功」して中身だけ空になる。鍵の列(ロット番号など)が
  無ければ**取り込まない** ── 空の鍵で総入れ替えすると、それまで
  使えていたデータまで消える
- 書き戻し(倉庫発注・入出庫履歴)も同じファイルへ。送信ID列と一意索引を
  自動で付け、二重送信を止める(`packaging_tool/outbox_sync.py`)
- **取り込んだ行は、取り込んだ直後に「送信済み」として記録し直す**
  (`outbox_sync.mark_all_sent`)。取り込みは総入れ替えで管理番号が
  振り直されるのに同期記録は古い行IDのままなので、これを飛ばすと
  取り込んだ行が「未送信」に見え、次の取り込みの前に走る書き戻しが
  **取り込み元から来た行をもう一度**送る ── 起動のたびに倍になる。
  古い記録を消すのも同じくらい大事で、残すと今度は新しく登録した行が
  「送信済み」に化けて二度と送られない

> 以前は Access(.accdb)で、Windows は ODBC・Linux は mdbtools という
> 分岐がありました。ドライバの有無で動いたり動かなかったりする厄介が
> あり、sqlite3 になってその分岐が丸ごと消えています。

### 設定は1画面に集める

`/settings` に全部あります。以前は置き場所が「データ」画面、拠点が
資材選択と棚検索の中、と散っていました。どこで何が変えられるのかを
探すこと自体が手間で、変えたつもりで変わっていない事故も起きます。

| 節 | 中身 |
|---|---|
| いまの状態 | 何が見つかっていて、何が足りないか(項目ごとに良し悪しを付ける) |
| 取り込みと反映 | 取り込み・書き戻し・適合範囲の再計算 + 進捗 |
| マスタ管理 | 梱包資材マスタの確認と修正(次の節) |
| 取り込み元 | 梱包資材マスタ / 仕掛台帳のフォルダ。サーバ側フォルダ参照つき(絶対・相対の両方) |
| 動作 | 拠点・起動時の自動取り込み・包装仕様書の図面URL |
| よく使う条件 | ロット検索の保存フィルタ(足すのは一覧、消すのはここ) |
| 最近の結果 | 直近の取り込み結果 |

並びは**触る頻度の順**。毎日押すものを上に、たまにしか触らないものを
下に置きます。保存は「置き場所」と「動作」で別々 ── 片方を直したい
だけのときに、もう片方まで送って他のタブの変更を上書きしないためです。

### マスタ管理 ── 直す先は取り込み元だけ

`packaging_tool/master_admin.py`。梱包資材マスタは起動のたびに黙って
読まれるだけで、中を見る手立ても直す手立ても画面にありませんでした。
値が違っていても、現場には「パレットが出ない」としか見えません。

**書き先は取り込み元ただ1つです。** 取り込みは総入れ替えなので、手元の
DBを直しても次の取り込みで消えます(**同じ事実を2か所に持たない**)。

```
画面 → 取り込み元へ書く → その表だけ取り込み直す → 手元が追いつく
```

最後の一手を飛ばすと、元は直っているのに画面の動きが変わりません。
**直したのに効かない**が一番たちが悪いので、その場で取り込み直します
(パレットなら適合範囲の再計算まで。`data_sync.import_master` と同じ)。

| 決めごと | 中身 |
|---|---|
| 行の指し方 | 取り込み元の `rowid`。手元の管理番号は取り込みのたびに振り直すので、**取り込み元の行を指しません** |
| 直せる表 | 資材課が持つ6表(`MANAGED`)。残りは見るだけで、**理由もその場に出す** |
| 直せる列 | `IMPORT_SPECS` ∩ 手元のスキーマ ∩ 取り込み元に実在する列。3つとも既にある事実を読むだけ |
| 型 | 手元のスキーマの宣言型。既定値の無い `NOT NULL` だけが必須 |
| 更新日時 / 登録日時 | 空欄なら保存時に入る。手で打たせる意味が無く、打ち間違いだけが増える |
| 誰が直せるか | **資材モードの権限**を持つ端末(いま開いているモードでは見ない) |
| 一度に出す行 | 200行。切ったぶんは必ず数で言う |

`WHERE` の無い `UPDATE` / `DELETE` は `source_db` が断ります。空の
`WHERE` は「全行」で、取り込み元は共有のマスタなので、1回の取り違えで
全員が困ります。

> **最初の1行だけは塞ぎません。** アクセス権限マスタに1行も登録が
> 無いあいだは直せます ── 塞ぐと、資材モードに入るための最初の1行を
> どこからも入れられなくなります。1行でも登録されればその時点で
> 閉まります。誰にも効かない行(条件を書き忘れた行)を入れて締め出された
> ときは、取り込み元の sqlite3 を直接開いて直してください。
> なお、この関門は**アクセス権限マスタの中身**で決まり、その中身は
> 動いている最中に変わるので、起動時に決める登録の出し分け
> (`warehouse.material_only`)では表せません。要求のたびに見ています。

### 起動のたびに開いてみる

`start_app._diagnose_sources()`。4つの取り込み元を1つずつ開いてみて、
**結果をログに残します**(大きさ・sqlite3 の印・付き添いファイル・
どの開き方で通ったか・表の数)。

「マスタが読めません」と言われたとき、これがあればログを見るだけで
原因が分かります。無ければ、こちらが端末に行って同じことをやり直す
ことになります。**診断で起動は止めません** ── 読めないことと、
アプリが使えないことは別です。

### 同じ行が2回入っていないか

`data_sync.duplicate_count()`。中身の同じ行を数えて設定画面に出します。
比べないのは**送るときに振られる番号だけ**(管理番号・送信ID)です
── 総入れ替えの取り込みでは番号が振り直されるので、番号で見分けると
何も見つかりません。

VER2.2.1 で直した「取り込むたびに発注が倍になる」不具合は、現場からは
**倍になってから**しか見えませんでした。同じことがまた起きたときに、
起きた側から気づけるようにしておきます。

## 8.5 一度に1つだけ書く

SQLite は1本しか書けません。取り込みの最中に受け入れを登録するなど、
書くものが重なると「データベースがロックされています」で片方が落ちます。

`app/__init__.py` の `_WRITE_LOCK`。**書く要求(GET / HEAD / OPTIONS
以外)を1つずつ通します。**

- **方法だけで決めます。** 経路ごとの表を持つと、画面を1つ足すたびに
  更新が要り、忘れたぶんだけ穴が開きます
- 待たせないものが3つ ── `/api/jobs`(進捗)・`/api/mode`(画面の
  切り替え)・`/api/log`。どれも**長い処理の最中に**呼ばれるもので、
  待たせると進捗が止まって見えます
- 放すのは `teardown_request`。`teardown_appcontext`(DB接続を閉じる)
  より**先に**呼ばれるので、接続より先に錠が返ります
- 再入可能(`RLock`)。要求の途中で書き戻しを呼んでも止まりません

## 9. 分かっている穴

塞いでいないことを、忘れないために書いておきます。

| 穴 | 中身 |
|---|---|
| 帳票の実寸 | 貼付ラベルはブラウザの余白設定に左右されます。実機で1枚出して確かめてください |
| マスタの変更履歴 | マスタ管理で直した内容は取り込み元に書きますが、**誰がいつ何を直したか**は残していません(改良案①) |
| CSV での一括編集 | マスタ管理は1行ずつです。何十行も直すときは取り込み元を直接触ることになります(改良案⑤) |
